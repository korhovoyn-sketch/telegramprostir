## Architecture

**PropSpace** is a Telegram Mini App for real estate management. It is a **static SPA** (Next.js 15 `output: 'export'`) deployed to Vercel. Because it is fully static, all `NEXT_PUBLIC_*` environment variables are baked in at build time — changing them requires a Vercel redeploy.

### Client-side navigation

There is **no Next.js router**. Navigation is a simple state machine in `src/store/appStore.ts` (Zustand). `src/app/page.tsx` renders a `switch` over `store.screen` and lazy-loads the matching screen component. `store.history` is a stack; `store.back()` pops it. The Telegram `BackButton` is wired to `store.back()` in `page.tsx`.

To navigate: `useAppStore().navigate('db-list', { dbId: '...' })`.  
To read params: `useAppStore().screenParams.dbId`.

### Screen pattern

Every file in `src/screens/` is a self-contained screen component. Screens pull their own data (Supabase hooks) and call `navigate()` / `back()` directly. There are no layout wrappers — each screen renders its full UI including header and bottom bar.

**Стан завантаження — заглушка мусить мати геометрію того, що її замінить.**
`SkeletonLoader` приймає `rowHeight` і екран передає СВОЮ висоту рядка: список баз
88, картка обʼєкта 200, компактний рядок 69, гостьовий дім 69; спільний дефолт 48
лишається для дрібних списків (`SkeletonList` — сповіщення, гості, команда).
Інакше прихід даних не «проявляє» екран, а перебудовує його: заглушка 48px стояла
на місці картки 178–228px. **Блока статистики в лоадері свідомо НЕМА** — усі пʼять
екранів малюють свій `.stat-g` ПОЗА гілкою `loading`, тож три плиткові заглушки
або дублювали справжні плитки (бази, дашборд рієлтора, гостьовий дім), або малювали
фантомний блок там, де статистики немає взагалі (обʼєкти бази, база рієлтора).
Гард — `loading-states.spec.ts`; CLS цього класу дефектів НЕ бачить (див. Testing).

### Auth flow

1. `SplashScreen` calls `restoreSession()` from `useAuth` → tries `supabase.auth.getSession()`, links session to `public.users` via `tg_id` extracted from the email `{tgId}@telegram.propspace.app`.
2. If no session → `WelcomeScreen` calls `loginViaTelegram(window.Telegram.WebApp.initData)`.
3. The Edge Function (`supabase/functions/telegram-auth/index.ts`) validates the HMAC-SHA256 Telegram signature, upserts the user in `public.users`, then uses `admin.generateLink` + `verifyOtp` to produce a real Supabase JWT.
4. On return: `setSession(access_token, refresh_token)` → `setUser(user)` → navigate based on `user.role`.

`public.users.id` (UUID) ≠ `auth.users.id`. The link is `tg_id` stored as the auth email prefix.

### Supabase client & type safety

`src/lib/supabase.ts` exports a lazy `supabase` proxy. It initialises `createClient` only once on first property access, avoiding SSR issues. Always import from `@/lib/supabase`, never construct a client inline.

**Type-safe queries**: All database queries must use types from `src/types/supabase.ts`. This file is auto-generated by Supabase CLI:

```bash
supabase gen types typescript --project-id your-project-id > src/types/supabase.ts
```

When you add new tables or modify schemas in migrations, regenerate this file immediately. Queries become type-safe:

```typescript
// ✅ Type-safe: result.data has correct shape
const { data } = await supabase
  .from('users')
  .select('id,role,email')
  .eq('tg_id', userId)
  .single()

// ✅ Validate RPC results with Zod
import { z } from 'zod'
const ClaimGuestSchema = z.object({
  property_id: z.string().uuid().nullable(),
  db_id: z.string().uuid().nullable(),
  error: z.string().nullable(),
})
const { data } = await supabase.rpc('claim_guest_link', { p_token })
const result = ClaimGuestSchema.parse(data)
```

### Edge Functions

All Edge Functions run on Deno v2. Use `Deno.serve(async (req) => { ... })` — the old `serve()` from `deno.land/std@0.168.0` is incompatible and causes EarlyDrop.

#### telegram-auth

`supabase/functions/telegram-auth/index.ts` validates Telegram `initData` via HMAC-SHA256, upserts the user in `public.users`, and returns a signed JWT. 

Key points:
- Pass `tg_id` to Supabase queries as `parseInt(tgUser.id, 10)` (BIGINT column rejects string comparisons)
- Session creation uses `admin.createUser({ email, password, email_confirm: true })` + `signInWithPassword` (not `generateLink`/`verifyOtp`)
- Password derived deterministically via `HMAC(SERVICE_KEY, email)` — never exposed to client
- Always validate HMAC with constant-time comparison to prevent timing side-channels

#### validate-upload

`supabase/functions/validate-upload/index.ts` validates file uploads before storage. Called by `usePropertyFiles.ts`:

```typescript
// In your hook:
const validateRes = await fetch(`${supabaseUrl}/functions/v1/validate-upload`, {
  method: 'POST',
  body: JSON.stringify({ propertyId, fileName, mimeType, fileSize }),
})
const { uploadUrl, storagePath } = await validateRes.json()
// Upload file to uploadUrl via signed POST
```

Validates:
- File MIME type (allowlist: PDF, DOC, DOCX)
- File size (max 20 MB)
- File count per property (max 10)
- User ownership of property

#### Deploying Edge Functions

Push to `main` with changes under `supabase/functions/**` triggers `.github/workflows/deploy-edge-function.yml`, which deploys **all four** functions (telegram-auth, validate-upload, telegram-bot, send-reminders). Requires `SUPABASE_ACCESS_TOKEN` + `SUPABASE_PROJECT_REF` secrets.

### Database schema & migrations

`supabase/migrations/` holds three files: `001_schema.sql` (canonical fresh schema), `002_rls.sql` (RLS + the `current_app_user_id()` helper), and `003_reconcile.sql` (idempotent — brings any existing/legacy DB up to spec and removes legacy artifacts).

Two non-obvious things that broke auth historically and must stay correct:
1. **`current_app_user_id()` resolves identity from the JWT *email* claim**, not a `tg_id` claim (Supabase doesn't add custom claims here). Email is `{tgId}@telegram.propspace.app`; the helper parses tg_id from it. A `tg_id`-claim version silently returns NULL → every RLS check fails → empty data everywhere.
2. **No `handle_new_user` trigger may exist on `auth.users`.** The Supabase starter template installs one that inserts into `public.users` with stale column names; it makes GoTrue fail with "Database error creating new user". `003_reconcile.sql` drops it. The edge function is the only thing that writes `public.users`.

The container running Claude Code on the web has **no outbound network** (Supabase host returns 403), so migrations cannot be pushed from here. `.github/workflows/migrate.yml` applies `supabase/migrations/**` on push to `main` (needs `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD` secrets). **One-time baseline required**: усі міграції до 040 застосовувались вручну, тож перед першим використанням запусти workflow вручну з `baseline=true` — він позначить наявні файли як застосовані без виконання SQL. До baseline міграції застосовуються в Dashboard SQL Editor; `supabase/verify_release.sql` перевіряє їхній стан одним запитом.

### Сповіщення: похідні блоки проти рядків у таблиці

`notifications` наповнює ВИКЛЮЧНО edge-функція `send-reminders`, і лише
`type='rent_reminder'` (тригерів у БД немає, клієнтський INSERT заборонений
035). Звідси головне правило екрана: **усе, що є СТАНОМ, а не подією, туди не
пишеться, а рахується на клієнті.**

Два таких блоки, обидва закріплені НАД датованими групами і обидва без кнопки
видалення (поки стан триває, прибирати нічого):

| блок | хук | джерело |
|---|---|---|
| «Терміни договорів» | `useLeaseAlerts` | `properties.lease_end_date`, вікно 30 днів |
| «Найближчі платежі» | `useUpcomingPayments` | `rent_payments` + `rent_payment_records`, вікно 14 днів |

**Чому платежі саме так, а не рядком у `notifications`.** Рядок зʼявився б лише
в день нагадування і лише якщо відпрацював крон — тобто вкладка «Платежі» була
порожня решту місяця В ПРИНЦИПІ. Це і була скарга власника. Похідний блок
натомість: працює без крону й міграцій, не дублюється при повторних прогонах
функції, і ЗНИКАЄ САМ, щойно платіж підтверджено (запис `paid` на цю дату).

**Дві пастки цього хука, обидві вже враховані:**
1. **Сума — не `rent_rate`.** Для `per_m2` це ставка ЗА МЕТР: показати її як суму
   до сплати означає намалювати $18 замість $1 800. Нормалізує `monthlyRent()` —
   той самий клас помилки вже ловили на картці календаря.
2. **День місяця обмежується довжиною місяця.** 31-е число в лютому інакше дає
   3 березня — платіж «поза своїм місяцем» і хибний порядок у списку.

**Тестова пастка:** платіжні гарди МУСЯТЬ морозити час (`clock.setFixedTime`).
Хук бере день місяця з розкладу, тож «через 3 дні» на 29-те число означало б уже
наступний місяць, а перша неоплачена дата лишалась би в цьому — той самий тест
читав би «прострочено на 28 днів» раз на місяць.

**Рівні терміновості спільні для обох блоків** — `.notif-i.lvl-soon/-critical/
-overdue` (inset-смуга 3px). Назва була `lease-*`; коли поруч став другий блок
із тими самими трьома рівнями, копіювати рецепт було б рівно тим дрейфом, через
який заведено `--shadow-seg-on`.

**Рядок закріпленого блоку — `<button>`, не `<div>`** (те саме правило, що для
`.sheet-row`). Рядки самих сповіщень лишаються `<div>`: усередині вони мають
кнопку видалення, а `<button>` у `<button>` — невалідна розмітка.

**Гонка двох завантажувачів — і чому порядку в екрані НЕ досить.**
`loadNotifications` викликають ДВОЄ: глобальний лічильник бейджа в `page.tsx`
(на `requestIdleCallback`, тобто в непередбачуваний момент) і сам екран. Обидва
пишуть у стор УВЕСЬ список, тож виграє той, хто відповів ОСТАННІМ, а не той,
чиї дані свіжіші. Наслідок: екран позначає все прочитаним, а через мить бейдж
повертається — доїхала відповідь на запит, ВИПУЩЕНИЙ РАНІШЕ, де `is_read` ще
false. Порядок `load().then(markAllAsRead)` захищає лише від ВЛАСНОГО запиту.
Лікує модульний `loadTicket` у `useNotifications`: кожна локальна мутація
(`markRead`, `markAllAsRead`, оптимістичне видалення) його збільшує, тож запит,
випущений до неї, права комітити вже не має.

**Гард на це ЛЕГКО зробити вакуумним, і перша версія такою й була.** Вона
робила найповільнішим ПЕРШИЙ запит, припускаючи, що перший — глобальний. Якщо
idle-колбек не встигав спрацювати до кліку, першим виявлявся запит екрана, він
же відповідав останнім — і тест був зелений НА ЗЛАМАНОМУ КОДІ. Робоча версія
гарантує порядок: чекає 2.5с (таймаут `requestIdleCallback` — 2000мс, тобто
глобальний запит точно випущений), тримає його 6с, і окремо перевіряє, що
запит справді був (`gets > 0`) — інакше вакуумність вернулась би мовчки.

### Roles

- `owner` — creates and manages property databases; sees `db-list` after login.
- `realtor` — subscribes to owner databases via share token; sees `realtor-dashboard` after login.
- New users get `role: 'owner'` by default but are sent to `role-select` if `user.role` is falsy.

**Запис редактора: `owner_id` мусить бути ВЛАСНИКА бази, і це не всюди надійно.**
`WITH CHECK` у 041 форсить це на сервері, але клієнт мусить проставити значення
сам. Два різні патерни в коді, і надійність у них різна: платежі
(`PaymentCalendarScreen`) і файли (`usePropertyFiles`) беруть `owner_id` з РЯДКА
обʼєкта — це стійко; `useProperties.createProperty/createProperties/moveToDatabase`
і `useFolders.createFolder` беруть його зі СТОРУ з фолбеком `?? user.id`, який
для редактора хибний за побудовою. Ланцюг тримає self-heal у
`DatabaseObjectsScreen` (екран сам довантажує свій рядок бази в стор) — гіпотезу
«холодний вхід ламає owner_id» перевірено і НЕ підтверджено, але гард на
інваріант поставлено (`team-writes.spec.ts`), і він упаде, якщо self-heal колись
приберуть як зайвий запит. Наслідок хибного `owner_id` на живому бекенді — саме
те, на що скаржаться: «створив обʼєкт, а він не зберігся».

**`property_views` для редактора — окремий випадок «мовчазної порожнечі».** RLS
на цій таблиці не віддає помилки за відсутності політики: вбудований підзапит
просто приходить порожній, тож `_view_count` стає 0. Редактор і власник дивляться
на ту саму базу й бачать різні цифри без жодного натяку чому. Лікує міграція 047
(`views_editor_select`).

**Team editors (не роль, а membership — 041).** `db_members` дає користувачу
право редагувати чужу базу (CRUD об'єктів, фото, файли, платежі), не змінюючи
`users.role`. Потік: власник створює інвайт у TeamScreen → deep link
`team_<invite_token>` → `claim_team_invite()` (SECURITY DEFINER, ідемпотентний).
Клієнт: `useDatabases` другим запитом тягне member-бази (тегує `_member: true`,
ids → `appStore.memberDbIds`), `isOwner`-шлюзи в екранах розширені
`memberDbIds.includes(dbId)`. **Owner-only лишаються**: шаринг-аналітика,
гості, команда — gated `db.owner_id === user?.id` (для об'єкта —
`property.owner_id`), НЕ через `isOwner`. Інваріант даних: усе, що створює
редактор, отримує `owner_id` власника бази (RLS `WITH CHECK` це форсить;
клієнт передає `owner_id` бази явно в `useProperties`/календарі). На бекенді
без 041 запит `db_members` падає — `useDatabases` це толерує (команда просто
вимкнена), тож фронт можна деплоїти до міграції.

### OWASP Top-10 checklist (verify every endpoint/mutation)

Before finalising any backend change, mentally run through:

| # | Threat | Mitigation in this project |
|---|--------|---------------------------|
| A01 | Broken Access Control | RLS on every table; `current_app_user_id()` is the only identity source |
| A02 | Cryptographic Failures | Passwords via `HMAC(SERVICE_KEY, email)` — never stored plaintext; tokens in Supabase JWT |
| A03 | Injection | PostgREST parameterised queries — no raw SQL. Zod validates all Edge Function inputs |
| A04 | Insecure Design | Share tokens server-enforced expiry; `prevent_privilege_escalation` trigger |
| A05 | Security Misconfiguration | `SERVICE_ROLE_KEY` Edge Function only; `ANON_KEY` read-only on client |
| A06 | Vulnerable Components | Pin `@supabase/supabase-js` and Zod versions in imports |
| A07 | Auth Failures | HMAC-SHA256 `initData` validation; 24h replay window (Telegram reuses initData across restarts); 20 req/min rate limit |
| A08 | Data Integrity | Cascade deletes tested; storage orphan cleanup on DB failure |
| A09 | Logging | Edge Function logs to Supabase Logs — never log tokens or user PII |
| A10 | SSRF | No server-side HTTP fetch to user-supplied URLs |

### Security rules (enforce always)

1. **Never expose internal errors to clients.** Edge Function 500 responses must not include stack traces or `detail` fields — log server-side only.
2. **RLS on every table.** Every `CREATE TABLE` must be followed by `ALTER TABLE … ENABLE ROW LEVEL SECURITY`. Use `current_app_user_id()` (not `auth.uid()`) — the JWT email claim is the identity source.
3. **No self-escalation.** The `prevent_privilege_escalation` trigger blocks users from modifying their own `plan`/`role`. Never call `updateProfile({ plan, role })` from the client — strip those fields before the query.
4. **initData must be HMAC-validated server-side.** Never trust `initDataUnsafe` alone. The Edge Function validates the full Telegram HMAC-SHA256 signature before issuing any JWT.
5. **Share tokens expire server-side.** The `db_share_lookup` RLS policy enforces `share_expires_at > now()`. Client-side expiry checks are UX only.
6. **Storage paths are per-property.** Upload paths are `{propertyId}/{timestamp}_{rand}.{ext}`. Never allow user-controlled path segments.
7. **SQL injections are impossible** via PostgREST parameterised queries — never build raw SQL strings with user input.
8. **Мутація мусить ДОВЕСТИ, що зачепила рядки.** PostgREST під RLS не вважає
   заблокований запис помилкою: `.delete()`/`.update()`, що не пройшли політику,
   повертають **порожній набір і NULL у `error`** — тобто «зробив» і «не мав
   права» на дроті нерозрізненні. Тому кожна мутація завершується `.select('id')`
   + `assertAffected(rows, expected, …)` з `lib/dbWrite.ts` (`.single()` —
   виняток: він сам падає з PGRST116). Гарди: `tests/unit/rls-silent.test.ts`
   (контракт) і `db-lifecycle`/`db-objects-ops` (на рендері).
9. **Спершу видали рядок, і лише ПОТІМ файли.** Наслідок №8 і найдорожчий урок
   цього класу: `deleteDatabase`, `batchDeleteProperties` і `deleteProperty`
   стирали storage ПЕРЕД рядком — заблокований DELETE давав тост «Базу
   видалено», база лишалась жива, а всі фото були знищені безповоротно. Правильний
   порядок: прочитати шляхи (після каскаду їх не дістати) → видалити рядок і
   довести це → чистити storage. Осиротілий файл витоком не є (політики читання
   привʼязані до рядків, яких уже немає), знищений при живому рядку — незворотна
   втрата даних.
10. **Права дає ВЛАСНІСТЬ рядка, а не роль акаунта.** `user.role === 'owner'`
    істинне для будь-якого власника незалежно від того, ЧИЯ база відкрита: акаунт
    із роллю owner, що прийшов у чужу базу гостьовим лінком, отримував FAB,
    «Редагувати» й «Дублювати». Шлюз — `row.owner_id === user?.id ||
    memberDbIds.includes(dbId)`. Гард: `db-menu-roles.spec.ts`.
11. **Політика на таблиці посилань мусить перевіряти, що ЦІЛЬ твоя.**
    `guest_links` мала лише `owner_id = current_app_user_id()` — тобто рядок із
    ЧУЖИМ `db_id` створювався легально, а після клейму третьою особою
    `is_guest_of_property()` віддавав усю базу жертви. Пор. `db_members` (041),
    де це виражено правильно: `db_id IN (SELECT get_owner_db_ids(...))`.
    Виправляти треба ОБИДВА боки — і запис (політика), і читання (предикат),
    інакше вже посаджені рядки продовжують діяти (міграція 046).

### TypeScript & Type Safety Rules

- **Strict mode**: `tsconfig.json` has `"strict": true`. Every value, parameter, and return must be typed.
- **No `any` type**: Except in `useTelegram.ts` where Telegram SDK types are partial; annotate with `// deno-lint-ignore no-explicit-any`.
- **Supabase queries**: Use types from `src/types/supabase.ts`. If you add a table, regenerate: `supabase gen types typescript --project-id ... > src/types/supabase.ts`.
- **RPC validation**: Always wrap RPC results with Zod schemas before using them.
  ```typescript
  const { data } = await supabase.rpc('claim_guest_link', { p_token })
  const validated = z.object({ error: z.string().nullable() }).parse(data)
  ```
- **Telegram SDK types**: Extend `TelegramWebApp` interface in `useTelegram.ts` when using new API methods (e.g., `setHeaderColor`, `setBackgroundColor`).

### Telegram Mini App Integration Rules

- **SSR Safety**: Never access `window.Telegram` directly in render. Use `useTelegram()` hook or `useEffect` with `typeof window !== 'undefined'` guard.
- **initDataUnsafe**: Safe for identity matching (cache key), NOT for access control. Always validate server-side via HMAC.
- **Dynamic theme**: Use `tg.themeParams.secondary_bg_color` and `var(--tg-theme-*)` CSS variables, not hardcoded colors.
- **Mobile-first**: 
  - Input `font-size: 16px` minimum (prevents iOS autozooming)
  - `overscroll-behavior: contain` on scroll containers (prevents chaining to Telegram webview)
  - `-webkit-overflow-scrolling: touch` for iOS momentum scrolling
  - Safe area: `--safe-top`, `--safe-bottom` CSS variables set by Telegram SDK

### Code style

- **No inline Supabase**: Always `import { supabase } from '@/lib/supabase'`, never `createClient()` inline.
- **Explicit columns**: Use `select('id,role,email')` not `select('*')`. This enforces RLS intent.
- **Error handling at boundaries**: Validate user input at API endpoints; trust internal code (RLS will reject bad access).
- **Derive state**: Use computed values (`const isAdmin = user.role === 'owner'`) instead of extra `useState` booleans.
- **No inline Supabase client construction** — always import from `@/lib/supabase`.
- **Explicit column lists in SELECT** — avoid `select('*')` in list views; fetch only columns the screen renders.
- **Derive state, don't sync it** — prefer computed values from existing state over extra `useState` booleans (e.g. `done = queue.every(...)`).
- **No comments that describe what code does** — only comments that explain non-obvious WHY (hidden constraints, workarounds).
- **Error handling at boundaries only** — validate at API/user-input boundaries; trust internal code and RLS.

### Remote session (Claude Code on the web)

The session-start hook (`.claude/hooks/session-start.sh`) runs `npm install` and, if `GH_PAT` env var is set, rewrites the git remote to embed the token so pushes work. Set `GH_PAT` in session Environment Variables via the Claude Code web UI.

  край. Половинна кнопка при 375px — це ~167px, і на цьому спалилось ШІСТЬ
  підписів (гірший, «Поділитись в Telegram», на 31px). Звідси правило: **підпис
  кнопки шита — короткий ДІЄСЛОВО**, обʼєкт дії каже заголовок («Підтвердити», а
  не «Підтвердити оплату»; «Створити», а не «Створити посилання»; «У Telegram»).
  Міряти треба `Range.getBoundingClientRect()` по вмісту кнопки проти її
  clientWidth мінус падінги — `scrollWidth` тут брехливий, бо текст не клiпається.
- **`_modal-audit.spec.ts` — інструмент, не гард** (як `_perf`/`_contrast`, у
  прогін не входить): `SHOTS_DIR=… PERF=1 npx playwright test _modal-audit`
  обходить УСІ 18 досяжних шитів, знімає кожен у файл для очного огляду і ганяє
  кожен через ТРИ шляхи закриття (бекдроп, Escape, кнопка). **Пастка заміру, вже
  наступана: перед заміром геометрії треба ЗНЯТИ фокус із поля.** Будь-який
  сфокусований інпут запускає `kbFallback`, а в безголовому браузері клавіатури
  немає — шит підіймається на 320px над порожнім місцем, і замір «шит
  притиснутий до низу» стає лотереєю. Історично джерелом фокуса був автофокус
  самих шитів (інвайт-шит проходив лише тому, що його таймер на 400мс не
  встигав добігти до порога); зараз автофокуса в шитах немає взагалі (див.
  Form & input rules), але сам обхід ТАПАЄ по полях — тож правило лишається.
- **`modal-a11y.spec.ts` — діалогова МЕХАНІКА, якої не бачив жоден інший тест.**
  `Modal.tsx` має повний набір APG-механіки (фокус усередину, повернення на
  опенер, Tab/Shift+Tab заперті, scroll-lock, свайп), і на все це не було ЖОДНОГО

  рефакторинг ламав її МОВЧКИ — і вже зламав: фокус не переходив у діалог ніколи
  (див. `mounted` у Form & input rules). Покрито: фокус усередину + повернення на
  опенер, замкнена пастка Tab, scroll-lock зі ВІДНОВЛЕННЯМ (протікле
  `overflow:hidden` лишає застосунок незгортним назавжди), свайп нижче порога без
  залишкових інлайнових стилів, свайп із тіла шита, тап по бекдропу під час
  запиту, клавіатурна досяжність рядків, `disabled` замість мертвого тапу,
  локальний Escape у полі. Два обовʼязкові антивакуумні прийоми: перевіряти, що
  фокусованих вузлів у шиті БІЛЬШЕ за два (інакше пастка тримає контейнер і тест
  порожній), і чекати понад 320мс перед «шит на місці» (див. Form & input rules).
- **`loading-states.spec.ts` — стани завантаження й стабільність лейауту.**
  **CLS тут майже сліпий, і це заміряно:** Layout Instability API рахує лише рух
  елементів, що ПЕРЕЖИЛИ кадр, а перехід скелетон → контент замінює піддерево
  цілком (заглушки видаляються, картки додаються) — під час реального
  завантаження `getEntriesByType('layout-shift').length === 0`, тоді як штучний
  зсув персистентного елемента дає 0.139. Тож CLS лишився на один клас (рух
  хрому), а решта міряється прямо: позиції `.hdr/.display/.stat-g/.seg/.tabbar/.fbtn`
  до і після приходу даних мусять збігтись, і висота заглушки мусить бути в межах
  ±30% від того, що її замінить. Плюс матриця станів: скелетон → контент,
  порожній стан, `RetryState` із РОБОЧОЮ кнопкою повтору.
  **Позиції хрому міряються НЕ на першому екрані, і це принципово.** Старт
  застосунку осідає САМ, один раз: `#app-root` живе на `var(--tg-vh, 100svh)`,
  тож поки mount-ефект `page.tsx` не запише реальну висоту від Telegram, лейаут
  стоїть на висоті вікна. Момент цього запису **залежить від середовища** —
  локально він встигає ДО першого скелетона, на CI (прод-білд під `serve`) —
  ПІСЛЯ. Поки замір «до» робився на db-list, у порівняння потрапляло саме це
  осідання: гард падав у CI на `.tabbar 593 → 512`, хоч локально був зелений
  10/10. **Два «очевидні» фікси не працюють, обидва перевірені:** очікування
  самої змінної `--tg-vh` локально є no-op (вона вже виставлена на момент
  скелетона), а очікування «стабільного кадру» завершується ДО осідання, якщо
  те запізнюється. Робоче рішення — спершу дати застосунку завантажитись
  ПОВНІСТЮ (дочекатись даних db-list), і тільки потім входити в базу й міряти
  db-objects, де хром уже осів і єдина змінна — прихід списку. Плюс гард від
  ВАКУУМНОСТІ: після заміру «до» скелетон мусить бути ще на місці, інакше
  `before === after` завжди і тест не перевіряє нічого.
- **`payment-calendar-order.spec.ts` — ЩО показуємо першим.** Блок «Немає
  розкладу» стояв ПЕРЕД місячними секціями, тобто екран «Календар платежів»

- **`devices.spec.ts` — ПʼЯТЬ ГЕОМЕТРІЙ ПРИСТРОЇВ, бо решта набору знає одну.**
  Усі інші тести ганяються на проєкті `iphone-se` (375×667), і це виглядало
  безпечно («найвужчий поширений iOS»), але хибне з обох боків: **вужче за 375
  буває** (Galaxy S8/S10e і вся бюджетна Android-родина — 360 CSS-пікселів), і
  **ширше теж ламає** (планшет розтягує мобільний лейаут удвічі). Обхід — усі
  25 кроків через `helpers/screens.ts` × 360×740 / 390×844 / 412×915 / 430×932 /
  744×1133; 375 свідомо ВІДСУТНІЙ, його вже проходить решта набору.
  **Три інваріанти, і кожен міряє те, чого не бачать інші два:** (1)
  горизонтальне переповнення — по `scrollWidth` КОНТЕЙНЕРІВ, а не елементів:
  чіп, що виїхав за край свого `overflow-x:auto` скролера, — це «ще не
  доскролено», а не дефект, і скролер клiпає вміст, тож на `scrollWidth` предка
  він не впливає — перевірка предків сама відкидає легальні випадки; (2) підпис
  CTA не вилазить за кнопку — через `Range.getBoundingClientRect()`, бо
  `scrollWidth` тут БРЕХЛИВИЙ: у `.mbtn`/`.fbtn` немає ellipsis, текст не
  клiпається, а просто лізе за край (той самий прийом, що в `modal-sweep`);
  (3) зона дотику 44px — через СПІЛЬНИЙ `TAP_DEBT`, який заради цього переїхав

  би за два раунди, і «нових порушень немає» перестало б щось означати.
  **Знайдений дефект — третій інстанс уже описаного класу.** Сканер QR
  переповнював екран на 3px: рядок «інпут + Додати» — флекс, а флекс-елемент за
  замовчуванням має `min-width:auto`, тобто відмовляється стискатись нижче
  intrinsic-розміру, який в інпута рахується від атрибута `size` (~20 символів),

  лікується так само, `minWidth: 0`. Переповнення було й на 375, просто його
  ніхто не міряв.

  дій картки («Редагувати / Дублювати / Платежі / Файли») читається як злиплий.

## Performance — заміряні цифри й межа

Замірні спеки живуть у `tests/e2e/_perf.spec.ts` і **не входять** у звичайний
прогін (`testIgnore: '**/_*.spec.ts'`). Запуск: `PERF=1 npx playwright test _perf
--workers=1`. Кожен мок-запит там штучно затримується на 120 мс — це LTE.

**Теплий старт** (кешований профіль, щоденний сценарій): FCP ~205 мс, екран
«Мої бази» ~250 мс, перша картка ~440 мс, 3 паралельні запити.

**Холодний старт** (перше встановлення, кешу немає): ~1150 мс — там неминучий
ланцюг `telegram-auth` → `auth/v1/user` → дані. Прогрів Edge-функції в
`SplashScreen` існує саме тому, що її холодний старт (10-30 с) — найбільша
затримка всього флоу.

**Що НЕ на критичному шляху** (і не має туди повертатись):
- `xlsx` (136 кБ gz) і `jsPDF` (102 кБ gz) — `await import()` у момент
  натискання «Завантажити», не при відкритті екрана експорту;
- `polyfills` (38 кБ gz) — Next віддає його з `noModule`, тож у webview Telegram
  він не вантажиться взагалі;
- **префетч екранів у сплеші**: одразу тягнеться ЛИШЕ екран, куди приведе цей
  старт (роль читається синхронно з `PROFILE_KEY`), решта — на
  `requestIdleCallback`. Раніше тягнулись усі сім, включно з екранами ролей, якими
  користувач ніколи не буде;
- **лічильник непрочитаних** — теж на idle. Він вилітав одразу на встановлення
  `user`, тобто РАНІШЕ за запит даних екрана, і конкурував з ним за зʼєднання,
  малюючи при цьому лише бейдж.

Разом ці два перенесення дали теплому старту ~160 мс (428 → 250 мс до екрана,
625 → 440 мс до першої картки), вхід у базу — 1197 → 873 мс.

### Плавність анімацій — заміряно, і головний висновок НЕ у цифрах кадрів

Інструменти (обидва `_`-префіксні, у прогін не входять):
`PERF=1 npx playwright test _anim-smoothness` друкує розподіл кадрів по кожній
анімації, `_blur-cost` — ізольований мікробенчмарк вартості скла.

**Найнадійніший сигнал — це ЯКІ властивості анімуються, а не цифри кадрів у
headless.** 42 з 48 `@keyframes` рухають лише `transform`/`opacity`. Двоє
рухали лейаут, обидва виправлені:
- `scanLine` — рухав `top` **2s infinite**, поки відкритий сканер, тобто
  перераховував лейаут кожен кадр без кінця. Тепер `translateY`; `translateY(%)`
  тут НЕ годиться (відсоток брався б від власних 2px смужки), тому хід іде від
  висоти рамки через `--scan-h`, яку виставляє екран. Замір після: 0 кадрів > 32мс.
- `progressFill` — рухав `width` .6s. Тепер `scaleX` + `transform-origin:left`
  (смуга однотонна, тож масштаб її не спотворює). Замір після: 0 кадрів > 32мс.

Лейаутні `transition` лишились лише клавіатурні (`.body`/`.modal-overlay`
padding-bottom, `.modal` max-height, `.mbtn` bottom) — вони СВІДОМІ, на
`max-height` навіть є тест «шит не СНЕПАЄ між висотами». Не «оптимізувати».
Третій свідомий лейаутний рух — `height` акордеона папок (`Collapsible`,
Web Animations API): розкрити список, не рухаючи висоту, неможливо в принципі.

**Але `opacity` разом із висотою — це вже НЕ ціна акордеона, а зайва робота.**
Обгортка фейдилась одночасно з рухом, тобто щокадру все піддерево папки (до 24
карток) складалось в офскрін-буфер і композитувалось з альфою — заради
переходу, який і так схований `overflow:hidden`. Тепер рухається лише висота, а
нуль для згорнутої секції виставляє хвіст `anim.finished`, тобто у спокої.
Гард: `folder-animation.spec.ts` («обгортка не фейдить під час руху»).

**`will-change` на НЕкомпозитній властивості — завжди мертва вага.**
`.fold-wrap` мала `will-change:height`: `height` не композитна, тож підказка не
пришвидшує нічого, зате тримається ПОСТІЙНО на кожній обгортці папки. Те саме
правило, через яке її немає на `.nav-wrap` і `.modal`, — просто там воно
формулювалось через backdrop root, а тут через безкорисність.

**Блюр під анімацією НЕ коштує нічого В CHROMIUM — і саме тому цей замір НЕ
можна поширювати на прод.** Ізольований бенчмарк (той самий елемент, різниця
лише в `backdrop-filter: blur(48px)`, 3 прогони поперемінно): p50 **16.7мс в
обох** випадках, 0 janky-кадрів З блюром проти 1 БЕЗ (шум). Chromium композитить
скло на GPU і не переблюрює регіон щокадру.

**А на iOS коштує, і тепер це ЗАМІРЯНО, а не припущено.** Тут довго стояло, що
поведінка WebKit — «єдине про плавність, що вимагає живого пристрою». Запис
екрана з iPhone (серпень 2026, 43.6 к/с) цю прогалину закрив. Профіль відкриття
шита меню, покадрова різниця:

```
f078  1 994 102 px   ← 67% ЕКРАНА за ОДИН кадр
f079    963 593
f080    409 594
f081     61 594      ← провал: кадр майже без руху
f082    191 857      ← рух відновився
```

Тобто перші ~60% шляху шит долав одним стрибком, а далі був загублений кадр —
класичний ривок. Причина: відкриття створює ДВА нові backdrop-шари (`.modal`
blur 48px + `.modal-overlay` blur 4px) поверх екрана, де вже 24+ карток
`.glass-s` зі своїм blur(28px). Тому блюр тепер **знімається на час руху шита**
(клас `moving` у `Modal.tsx` → `.modal.moving,.modal-overlay.moving`) — рівно
той прийом, що вже роками працює в акордеоні папок (`.fold-anim`), де в
`Collapsible.tsx` прямо написано, що переблюрювання щокадру «is what made it
stutter». Стара примітка «спроба глушити блюр була відкочена, виграшу немає»
стосувалась ВИКЛЮЧНО Chromium і більше не діє як аргумент.

**Інструмент: `scripts/analyze-recording.py`.** Приймає запис екрана, друкує
покадрову різницю і сам позначає провали (кадр рухався втричі менше за сусідів)
та стрибки (>40% екрана за кадр). Це єдиний спосіб перевірити плавність на iOS —
локальний прогін не побачить ані дефекту, ані фікса. Верифікація будь-якої
зміни плавності = новий запис того самого жесту + порівняння профілю.

**Пастка замірів, вже наступана:** цифри свайпу в `_anim-smoothness` (p50 36–53мс,
майже всі кадри поза бюджетом) — це ЗАБРУДНЕНИЙ замір: синтетичні `touchmove`
відправляються з rAF-колбека, тож у «час кадру» входить робота самого тесту. На
такому не можна нічого доводити — саме тому знадобився ізольований `_blur-cost`.
Друга пастка, теж наступана: `reuseExistingServer` локально true, тож пробіг міг
підхопити ЧУЖИЙ `serve out` з попереднього прогону — і впасти на
«Missing environment variable: NEXT_PUBLIC_SUPABASE_URL», бо голий `npm run build`
(без `webServer.env`) пече бандл без змінних. Запускати інструменти під `CI=1`.

**Межа, задокументована замірами:** список НЕ віртуалізований. 25 обʼєктів —
~870 мс до появи, 200 обʼєктів — **~1780 мс**, 10 800 вузлів DOM і 200 шарів
`backdrop-filter`. Кадри при цьому лишаються по 17 мс (Chromium), але на iOS
кожен блюр коштує дорого — той самий бюджет, через який `.fold-anim` глушить
блюр на час анімації. Якщо бази виростуть до сотень обʼєктів, правильний фікс —
віконне рендерення списку, а не CSS: `content-visibility:auto` пробувався і
**виграшу не дав**, бо вузьке місце не в палітрі, а в тому, що React створює всі
200 компонентів.

## Читабельність — заміряно, не на око

`tests/e2e/contrast.spec.ts` — ГАРД у прогоні; `_contrast.spec.ts` лишився
принтером найгірших місць (`PERF=1 npx playwright test _contrast`), замірний код
спільний у `helpers/contrast.ts`. Контраст рахується по РЕАЛЬНОМУ рендеру: знімок робиться двічі —
звичайний і з прозорим текстом, другий дає чистий фон, у ньому усереднюються
пікселі під кожним текстовим блоком. Аналітично тут не порахувати: текст — біле
з альфою, під ним шари скла над градієнтом, який СВІТЛІШАЄ донизу (низ
`.bg-blue` — це #5480dc, той самий колір, що йде в `barColor`).

**Чому це важливо саме тут:** дим-текст на світлішому низу градієнта — не
косметика. Замір показав поверх «10» і площу «175.8» на 2.45:1, тобто самі ДАНІ
були нижче порогу, а не підписи.

Шкала тексту — ЧОТИРИ токени: `--t1` #fff, `--t2` .84, `--t3` .74, `--t4` .64
(альфи підняті з .72/.55/.46 після заміру). **Колір тексту беруть лише з них** —
guard `design-tokens.test.ts` («шкала кольору тексту») падає на новому
захардкодженому `rgba(255,255,255,…)`. Попередній guard цього не ловив, бо
порівнював лише з наявними значеннями токенів: плитки дашборда мали `.48`, воно
не збігалось із `.46` — і лишались нижче AA, поки їх не перевели на токен.

**Залишковий борг — ЗАМОРОЖЕНИЙ числом, не «прибрати колись».** `CONTRAST_DEBT`
у `contrast.spec.ts` перелічує класи з причиною, `FROZEN` — скільки блоків нижче
AA дозволено на екран (db-list 0, db-objects 6, property-detail 0, profile 6), тож
борг не росте і ВСЕРЕДИНІ дозволеного класу. Рішення власника: правити ДАНІ,
підписи лишити — усе, що лишилось, це підписи й капшени:
- `.dash-l` / `.dash-sub` — підпис і капшен плитки дашборда над **світлим
  тонованим** блоком: лікується темнішим фоном, брайтити біле нікуди;
- `.bdg-busy` / `.bdg-info` — тонований бейдж, foreground на тлі своєї ж заливки;
- `.fr-seg-b` — неактивний сегмент (мова/валюта в Профілі): приглушеність тут і є
  станом;
- `.over > span` — оверлайн секції Профілю, 11px/600 uppercase;
- 13 правил із власним білим-з-альфою лишаються в allowlist джерельного гарда —
  тост, галерея, сплеш, hero, превʼю експорту, неактивна іконка таббару.

**Що ВИЙШЛО з боргу:** `.obj-tot-l` / `.obj-tot-v` / `.obj-tot-sub` — смузі
підсумку картки дали темніший ґрунт (`background: var(--glass-card)`), і всі три
піднялись над AA. Це і є той «темніший блок», який борг вимагав; лікувати альфою
тексту було нічим. Урок ширший: **градієнт екрана світлішає донизу, тож будь-яке
зміщення контенту вниз ЗНИЖУЄ контраст** — після підняття висоти сегментів на
10px `.obj-tot-sub` сам собою впав з 4.5 до 4.38.

**Тап-таргети — 44px по ФАКТИЧНІЙ зоні, і гард саме на ній.** `ui-audit` міряє
бокс і лишається на 32px (він ловить справді крихітні контроли); Apple HIG 44
перевіряє `contrast.spec.ts` через `elementFromPoint`, бо `::after` розширює зону
дотику НЕ змінюючи геометрію — для боксового заміру він невидимий. Заморожений
борг: `.view-seg-b` (38px по ширині) і `.obj-act-btn` (рядок дій картки, ~35px —
свідоме рішення, див. нижче).

**ПАСТКА, через яку «виправлене» роками не працювало.** `::after` обрізається
будь-яким предком **або самим собою** (pseudo-елемент належить власному box'у) із
`overflow ≠ visible`, і тоді зона дотику лишається розміром бокса, хоч у CSS
виглядає розширеною. Так було з `.seg-b` (власний `overflow:hidden` під
`text-overflow:ellipsis`), `.notif-tab` (контейнер `.notif-tabs` має
`overflow-x:auto`, що за спекою робить і `overflow-y` не-visible) — і, третім
інстансом того ж класу, знайденим пізніше (серпень 2026), `.fr-seg-b` (мова/
валюта в Профілі): той самий `overflow:hidden` під ellipsis, що й `.seg-b`, але
його свого часу помилково поклали в `::after`-список замість списку нижче. Усі
три «мали» 44px, а фактично 34, 38 і 36. Їм підняли РЕАЛЬНУ висоту (padding/
min-height) і забрали з `::after`-правила; лишились там тільки `.view-seg-b` і
`.hdr-back`, де дійсно нічого не клiпає.

Це не побачив і сам зонд: у ньому влучанням вважалось `h.contains(e)`, тобто тап
в ОБГОРОДКУ (`.seg`, рядок картки) зараховувався кнопці. Після виправлення на
`h === e || e.contains(h)` розрив і проявився. Мораль для будь-якого майбутнього
зонда: «влучив у предка» ≠ «влучив у контрол».

**НЕ чіпали свідомо:**
- `.obj-act-btn` (кнопки в рядку картки — «Редагувати / Дублювати / Платежі /
  Файли»): над ними тіло картки, яке відкриває обʼєкт. Розширення вгору вкрало б
  його тапи — це рішення про висоту рядків картки, не про сам контрол;
- `.view-seg-b` (перемикач «Картки/Компактно», 38px по ширині): квадратні
  кнопки-іконки впритул одна до одної в спільній обгородці — розширення вкрало б
  тап у сусідню.

Виміряний зонд бере ФАКТИЧНУ зону дотику через `elementFromPoint`, а не бокс
елемента — інакше `::after` виглядав би невидимим для гарда. Дві пастки зонда
під час розробки: (1) міряти від `window.innerHeight` замість верху таббару —
оболонка (`--tg-vh`) нижча за вікно, тож усе після 512px просто нижче фолду, не
«вкрадено»; (2) не фільтрувати по `window.innerWidth` — таб у горизонтально
прокрутному контейнері (`.notif-tabs`) може фізично лежати за краєм екрана
(ще не проскролений), і `elementFromPoint` там завжди `null`.

## Form & input rules (вистраждано на iOS)

- **НІКОЛИ `type="number"`.** Контрольований number-інпут повертає `''` на проміжному стані (друга крапка/кома) — «введене зникає»; скрол міняє значення. Правильно: `type="text"` + `inputMode="decimal|numeric"` + `sanitizeDecimal`/`sanitizeInt` з utils в onChange. Санітайзер розпізнає вставлені розрядні роздільники («1,200,000» → 1200000, НЕ 1.2).
- **`:hover` тільки під `@media (hover: hover)`** — інакше на iOS перший тап «залипає» (FAB лишається збільшеним, рядки підсвіченими). `:active` — поза media, це тач-фідбек.
- **Каретка під backdrop-filter** малюється зі зміщенням (WebKit-баг) — глобальне правило дає текстовим інпутам `translateZ(0)` (окремий шар). НЕ поширювати на date/select: у них немає каретки, а стекінг-контекст може клiпати нативні поповери.
- **Модалки** (`components/ui/Modal.tsx`): клавіатуро-свідомі (`--keyboard-h`), скрол-тіло + sticky-екшени, бекдроп-тап закриває, Escape закриває ЛИШЕ верхню модалку стеку (module-level `modalStack`). Не додавай window-keydown у вкладені компоненти.
- **Кільце фокуса на ПОЛІ живе під `@media (pointer: fine)`, і це не смак.**
  `:focus-visible` НЕ означає «лише з клавіатури»: за специфікацією елемент, що
  очікує введення тексту, матчить його ЗАВЖДИ, хоч би як його сфокусували, і
  WebKit це реалізує. Тобто кожен тап по полю в Telegram малював синю рамку —
  скріншот власника (серпень 2026). Коментар у CSS при цьому стверджував
  протилежне («тач кільця не отримує»), тож помилка була не в правилі, а в
  ПЕРЕКОНАННІ, на якому воно стояло. Для КНОПОК і рядків шитів твердження
  правдиве, тому їхні правила лишаються безумовними — і саме їх міряє
  `modal-a11y` («фокус із клавіатури ВИДНО»). Ціна, названа свідомо: на
  планшеті з апаратною клавіатурою (`pointer: coarse`) кільця на полі не буде.
  Гард: `inputs.spec.ts` → «тап по полю НЕ малює кільце фокуса».
- **У шитах НЕМА `autoFocus` — узагалі, і тап-ініційований теж.** Рішення
  власника («не фокусувати автоматично взагалі»), і причина не в стилі, а в
  тому, ЩО САМЕ робить тап по «+ Нова папка» / «Перейменувати»: він МОНТУЄ
  поле, тобто міняє висоту шита — а фокус у той самий кадр додає пробу
  `kbFallback` (350+200мс), `padding-bottom .25s` оверлея і `max-height .25s`
  шита, усе поверх 48px-блюру. Саме це власник описав як «відразу клавіатура
  перекриває або піджимає». Клавіатуру підіймає ТАП КОРИСТУВАЧА по полю, ціною
  одного зайвого дотику. Перший підхід лишив тап-ініційовані фокуси як «пряму
  відповідь на дію» — і саме через це дефект прожив ще раунд. Екранні
  `autoFocus` (`CreateDatabaseScreen`, `PropertyFormScreen`) — інший випадок і
  НЕ чіпаються: там немає ні слайд-анімації шита, ні клавіатурної корекції
  оверлея. Гард: `design-tokens.test.ts` → «клавіатура в модалках».
- **Блюр знімається на ВЕСЬ час руху шита — і виїзду, і клавіатурного.**
  `moving` гасне на `animationend` відкриття, тож клавіатурні кадри йшли повз
  нього; `kbMoving` (той самий клас на DOM, щоб не ламати наявні очікування
  `.modal-overlay.moving → 0`) зводиться на зміну висоти > 20px і гасне через
  300мс. Поріг обовʼязковий: пристрій шле висоту кількома тіками, і без нього
  хвіст тримав би блюр знятим довше за сам рух. Гард: `modals.spec.ts` → «блюр
  знято, поки шит їде під клавіатуру» (перевіряє і ПОВЕРНЕННЯ скла — знятий
  назавжди блюр це вже не оптимізація, а зміна вигляду).
- **Локальний фолбек висоти клавіатури (`kbFallback`, 320px) МУСИТЬ вміти самоскасуватись.** Коли платформа не звітує висоту клавіатури за `KB_PROBE_MS`+`KB_CONFIRM_MS` (550мс), модалка вмикає фейковий ліфт. Реальний прод-баг (відео користувача): на iOS-оверлеї `visualViewport.resize` іноді приходить ПІЗНІШЕ за цю пробу — фейкові 320px лягали ПОВЕРХ реальної клавіатури, що вже розкривалась, і поле («Орендар» у формі оренди) сіпалось, доки користувач не забирав фокус. Фікс — два шари: (1) `KB_CONFIRM_MS` (200мс) — другий замір ПІСЛЯ першої проби, а не миттєве вмикання фолбека на межі; (2) окремий `useEffect`, підписаний на `visualViewport.resize` ПОКИ `kbFallback` активний, знімає його, щойно приходить довірена (`reportedKeyboardPx() >= KB_TRUSTED_PX`) реальна висота — інакше локальні 320px пережили б справжню клавіатуру аж до blur поля. **Тестова пастка:** е2e не може показати нативну клавіатуру — підміна мусить бути РЕАЛІСТИЧНОЮ (`Object.defineProperty(visualViewport, 'height', {get: () => …})` + `dispatchEvent('resize')`), а не прямий запис у `--keyboard-h` з подальшим голим `resize`: `page.tsx`'s `applyKeyboardFromVV` теж слухає цю подію і, порахувавши висоту з РЕАЛЬНОГО (незміненого) `visualViewport.height`, миттєво стирає будь-яке ручне значення змінної до того, як реконсиляція в `Modal.tsx` встигає його прочитати. Другий нюанс заміру: `padding-bottom` іде transition (.25s) — читати `computedStyle` треба ПІСЛЯ переходу, інакше замір ловить проміжне значення (спостерігали нестабільні 108–191px замість фінальних 260).
- **КЛАВІАТУРА: підйом НА ФОКУС, звірка на `resize`. Слідкувати за нею НЕМОЖЛИВО
  — це перевірено джерелами, а не припущено.** Заміряно на записі з iPhone:
  клавіатура рушає на 3543 мс, шит — на 3691 мс, тобто **лаг 148 мс**, і ще
  ~220 мс їде; увесь цей час поле, по якому тапнули, перекрите. Причина не в
  тривалості переходу, а в ДЖЕРЕЛІ: `visualViewport.resize` на WebKit приходить
  ОДИН раз, наприкінці анімації клавіатури.
  **Перша редакція фікса пропонувала rAF-стеження за `visualViewport` — і це
  було б марно:** WebKit свідомо не перебудовує лейаут щокадру анімації, а потік
  подій під час руху дає лише `geometrychange` з VirtualKeyboard API, і той є
  ТІЛЬКИ в Chromium. Telegram власного API для клавіатури не має взагалі
  (Telegram-iOS #1296/#1298/#1410/#1637, Mini-Apps #33/#34, telegram-apps
  #732/#737 — усі відкриті; `interactive-widget` iOS-клієнт ігнорує).
  **Робочий підхід — стартувати ОДНОЧАСНО:** клавіатура iOS їде ~0.25s, наш
  `transition` теж 0.25s, тож `focusin` одразу пише `--keyboard-h` із КЕШУ
  попереднього відкриття, а `resize` потім лише звіряє (перетирає, не додає) і
  кеш поповнює. `focusout` одразу вертає 0 — інакше повернення вниз лишалось би
  снепом в один кадр (заміряно: 43.6% екрана за кадр).
  **Чому це не дає подвійного ліфта:** кеш наповнюється ЛИШЕ з
  `innerHeight − vv.height > 0`, а таке можливе тільки там, де клавіатура
  НАКРИВАЄ. Клієнт, що стискає webview, у кеш не потрапляє ніколи, тож
  передбачливий підйом там просто не вмикається (плюс явна перевірка
  `layoutShrunkByKeyboard()`). Непідтверджений за 600 мс підйом знімає сам себе
  — апаратна клавіатура на планшеті інакше лишила б шит піднятим.
  **`offsetTop` у формулу НЕ додавати** — двічі з різних причин: він смикається
  на кожному кадрі скролу (через це його колись і прибрали), а в iOS 26 ще й не
  повертається в 0 після ховання клавіатури (Edge #3828, Apple Forums 797097).
- **Закриття по успішній дії НЕ анімується, і клон на розмонтуванні цього НЕ
  лікує — спроба зроблена й відкочена.** Заміряно: після «Зберегти» 63.5% екрана
  змінюється за ОДИН кадр. Причина структурна: викликачі гейтять шит на
  нульованих даних (`{setupProp && <Modal…>}`), тож `setSetupProp(null)` знімає
  компонент миттєво і двофазне `requestClose` не встигає НІКОЛИ.
  **Чому клон оверлея (`cloneNode` на розмонтуванні) не підходить:** він лишає в
  DOM ДРУГИЙ `.modal`/`.modal-overlay` на час виїзду. Це ламає дві речі одразу —
  `.modal-overlay ~ .modal-overlay{background:rgba(0,0,0,.32)}`, тобто свіжо
  відкритий шит отримує ПРИГЛУШЕНЕ затемнення вкладеного (див. правило про
  вкладений оверлей нижче), і будь-який `locator('.modal')`, випущений одразу
  після закриття попереднього шита (повний прогін дав 8 падінь).
  **Правильний шлях — проп `open` на всіх 13 інстансах** плюс хелпер-засувка, що
  тримає останнє НЕнульове значення даних на час виїзду. Це окремий раунд, а не
  хвіст клавіатурного: зміна контракту всіх викликачів вимагає власної
  верифікації.
- **ПОДВІЙНИЙ ЛІФТ — головна пастка модалок. Перед будь-якою зміною клавіатурної
  логіки `Modal.tsx` прочитай цей пункт цілком.** Шит піднімається над
  клавіатурою ДВІЧІ, якщо лейаут уже стиснувся, а модалка думає, що ні: вона
  додає власний `KB_FALLBACK_PX` поверх уже врахованої клавіатури. Симптом
  однозначний і його легко впізнати на скріншоті — шит у ВЕРХУ екрана, під ним
  ДІРА з розмитим контентом, унизу клавіатура. Заміряно на скарзі користувача
  (модалка «Папки»): вікно 700px, клавіатура 300px → оверлей 400px,
  `padding-bottom: min(320px, 55vh=220)` = 220px → шит займає верхні 26%, діра
  31%, клавіатура 43%. Зламавши фікс, отримали відрив **202px** проти
  передбачених 220 — тобто діагноз перевіряється арифметикою, а не на око.
  **Правило: «чи клавіатура вже врахована» НЕ МОЖЕ мати одне джерело правди.**
  `layoutShrunkByKeyboard()` питає САМ Telegram (`viewportHeight` vs
  `viewportStableHeight`) — і рівно на цьому ламалось: клієнт стискав webview,
  але цих значень не оновлював. Тому `layoutCompressed()` у `Modal.tsx` тримає
  ДРУГИЙ, незалежний від платформи сигнал: `window.innerHeight` стало меншим за
  висоту на момент МОНТУВАННЯ шита (`baseInnerHRef`). Хибно спрацювати він не
  може — якщо клавіатура вже була відкрита при монтуванні, база враховує її, і
  різниця нульова або відʼємна. Додаючи третій режим клавіатури, додавай і
  третій сигнал, а не «уточнюй» наявний.
- **Хибно ввімкнений ліфт мусить знімати себе на ОБИДВІ події —
  `visualViewport.resize` І `window.resize`.** При СТИСКАННІ webview змінюється
  саме `window`, і клієнт, що не оновлює `visualViewport`, інакше лишив би шит
  відірваним аж до блура поля.
- **`visualViewport.height` НЕ зменшується, коли клавіатура ПЕРЕКРИВАЄ webview
  — заміряно 667px при відкритій клавіатурі.** Тому будь-яка арифметика виду
  «висота вікна мінус константа» для обходу клавіатури дає нісенітницю: перша
  версія фікса відступу під плаваючою CTA так отримала зазор 368px і зробила
  ГІРШЕ, ніж було (4 перекриті поля замість 1). Правильно — брати межу з
  геометрії РЕАЛЬНОГО елемента (`getBoundingClientRect().top` кнопки), а не
  рахувати від вікна.
- **Плаваюча кнопка НАД формою завжди воює з полями.** `.mbtn` без `mbtn-flow`
  накривала поля на 7–27px, і жоден зазор цього не лікує остаточно. Тому
  первинна дія форм (створення бази, форма обʼєкта) свідомо IN-FLOW —
  `mbtn-flow` існує саме для цього. `field-obstruction.spec.ts` — гард; якщо він
  почав падати після дизайн-зміни, це не «прикрутити допуск», а сигнал, що
  кнопка знову накриває введення.
- **Тестова матриця клавіатури — ТРИ режими, не два.** Перекриття
  (`visualViewport` шириться, `--keyboard-h` є), стискання зі звітом
  (`__tgViewportStable` + `__tgKeyboard`) і **стискання БЕЗ звіту** —
  `page.setViewportSize()` ріже висоту, а `__tgViewportStable`/`__tgKeyboard`
  НЕ чіпаються. Третій режим — це саме прод-клієнт користувача, і саме він не
  був покритий, коли баг проліз. Гард: `modals.spec.ts` → «шит НЕ підстрибує
  вгору, коли webview стиснувся, а Telegram про це не звітує».
- **Гард «не закривай, поки летить запит» живе В `Modal.tsx`, і НІКОЛИ у
  викликача.** Три екрани робили `onClose={() => !creating && setShow(false)}` —
  і це було ГІРШЕ за відсутність гарда. Закриття двофазне: `requestClose` вішає
  клас `closing` (шит зʼїжджає за екран, оверлей стає `pointer-events:none`), і
  лише ПОТІМ `finishClose` виставляє `firedRef=true` і кличе `onClose`. Якщо той
  відмовляється закривати, шит лишається змонтованим, але невидимим і мертвим, а
  `firedRef` назавжди блокує будь-яке наступне закриття — модалку неможливо ні
  закрити, ні відкрити знову до перемонтування екрана. Досягалось звичайним
  тапом по бекдропу, поки на LTE летів запит. Гард тепер один, у `requestClose`,
  за `busyRef`. Гард на це — `modal-a11y.spec.ts` («тап по бекдропу під час
  запиту…»), і він свідомо ганяє запит, що ПАДАЄ: при успіху шит розмонтує
  `setState` викликача, тобто застрягання не проявиться.
- **`busy` у `Modal.tsx` мусить мати дзеркало в ref.** Ефект Escape має
  `[]`-залежності, тож захоплює `requestClose` із ПЕРШОГО рендера, де `busy` ще
  `false` — Escape обходив би гард закриття. Той самий ref робить re-entry гард
  синхронним (стан оновлюється асинхронно, тож два швидкі тапи проскакували
  обидва). Правило ширше: будь-який гард, який читають ефекти з `[]`, живе в ref.
- **Ефект, що чекає на DOM, не може мати `[]`-залежності — потрібен `mounted`.**
  Портал існує лише в браузері (статичний експорт пререндерить на Node), тож при
  `[]` ефект біжить на першому коміті, коли компонент повернув `null` і
  `modalRef` порожній, і більше не повторюється. Так фокус НЕ переходив у діалог
  НІКОЛИ: він лишався на кнопці-опенері, і читалка озвучувала екран ПІД шитом.
  Жоден із 202 тестів цього не бачив, бо Tab ніхто не натискав.
- **Клікабельний елемент шита — `<button>`, не `<div>`.** Фокус-пастка
  (`Modal.tsx`) шукає саме фокусовані вузли, тож із `<div>` Tab у меню бази
  циклився між «Скасувати» і нічим, а рядки меню були недосяжні і з клавіатури, і
  для читалки. Виправлено класом: `.sheet-row` (меню бази, пікери, керування
  шарингом), `.fr-seg-b` (усі сегментні перемикачі), `.logout`, `.del-acc` — усі
  зі скиданням UA-стилів кнопки в CSS. Гард: `modal-a11y.spec.ts` («рядки шита
  досяжні з клавіатури»).
- **«У процесі» — це `disabled`, а не зняття обробника.**
  `onClick={busy ? undefined : …}` лишає `cursor:pointer` і `:active`: рядок
  підсвічується під пальцем і не робить НІЧОГО. Неактивність показує КОЛІР
  (`--t4`), не `opacity` — над темним шитом прозорість зʼїдає елемент.
- **«Скасувати» — через `actions`, а не власна кнопка в тілі шита.** З `actions`
  приходить sticky-позиція, safe-area (інакше кнопка лягає під home-індикатор) і,
  головне, клавіатурна корекція: `clearStickyActions` виходить ОДРАЗУ, якщо
  `.modal-actions` у шиті немає взагалі — тобто саме input-модалки без `actions`
  (пікери, «Папки») не отримували її зовсім. Заливку первинної кнопки дає
  `btn-glass`, який додає лише шлях `actions`; кнопці, що свідомо лишається в
  потоці, клас треба брати з `modalBtnClass()`, а не переписувати руками.
- **Свайп закриття має міряти ШВИДКІСТЬ, і замір потребує підлоги по часу.**
  Поріг лише по відстані (96px) на короткому шиті — це майже вся його висота, тож
  рішучий флік читався як «жест не працює». Але ділити на `dt=1мс` не можна: один
  кадр, що прийшов упритул до попереднього, дає 25px/1мс і закриває ПОВІЛЬНИЙ
  жест. Звідси `V_MIN_DT_MS = 8` (кадр швидше за 8мс — це вже понад 120Гц, тобто
  шум). **Тестова пастка тієї ж природи:** синтетичні `touchmove` без затримок між
  ними описують не «повільний рух», а миттєвий стрибок — хелпер `drag()` у
  `modal-a11y` тому РОЗНОСИТЬ кадри в часі (`stepMs`), а флік — це той самий
  хелпер із 16мс. Наступали: гард «повільний рух не закриває» падав саме через це.
- **Інлайновий `transition`, виставлений на час snap-back, треба знімати
  БЕЗУМОВНО, а не лише на `transitionend`.** У найчастішому випадку — тап по
  хедеру без руху — transform не змінюється, тож `transitionend` не приходить
  НІКОЛИ, і мертвий `transition: transform .24s` лишається на шиті назавжди,
  перебиваючи анімацію закриття. Заміряно зондом: `+500ms` без таймера прибирання
  все ще `"transform .24s var(--ease-out)"`. **Гард на це легко зробити хибно
  проходячим:** `drag(…, 0)` НЕ відтворює тап — у ньому є move-події і шлях інший,
  зі зламаним фіксом такий гард лишався зеленим. Тап — це touchstart + touchend
  БЕЗ touchmove.
- **`.modal` не має постійного `will-change`** — шит уже сам собі backdrop root
  через `backdrop-filter`, тож шар нічого не пришвидшує, зате тримається назавжди
  (два вкладені шити — два шари з блюром 48px). Та сама причина, що для
  `.nav-wrap`.
- **Вкладений оверлей не затемнює вдруге, і це вирішено СЕЛЕКТОРОМ, не станом.**
  Два оверлеї по `rgba(0,0,0,.6)`+`blur(4px)` давали ≈0.84 і подвійний блюр,
  розмиваючи й сам шит під підтвердженням. Обидва — портали в `<body>`, тобто
  сусіди, тож `.modal-overlay ~ .modal-overlay` матчить лише той, під яким уже є
  інший, і сам себе скасовує, коли нижній зникає. Реактивного стану для цього не
  треба (і `modalStack` для нього не годиться — це не стан React).
- **Локальний Escape у полі всередині шита потребує `stopPropagation()`.** Modal
  слухає Escape на window; без цього Escape, яким скасовують правку назви, зносив
  УСЮ модалку. **Гард на це легко зробити вакуумним:** шит живе в DOM ще ~320мс
  із класом `closing`, тож `toHaveCount(1)` збігається на першому полінгу ПОСЕРЕД
  виходу і проходить навіть зі зламаним фіксом. Треба пауза > 320мс, потім
  перевірка `.modal.closing → 0`. Наступали — гард спершу «пройшов» обидва боки.
- **PropertyFormScreen — три режими**: create / edit (`propertyId`) / duplicate (`duplicateId` — префіл усього крім орендаря/дат/фото, ім'я через `nextCopyName`). Create-режим: чернетка автозберігається в localStorage (600мс debounce, ключ per user+db), відновлюється з тостом «Очистити»; bulk-режим (`count` > 1) — редаговані рядки (ім'я + площі, фолбек на спільні поля), збереження ОДНИМ insert-ом з послідовним `sort_order`, `bulkCreateNames` пропускає зайняті імена (для цього create-режим ТЕЖ вантажить список).
- **Валюта в підписах**: `currencySymbol(user?.currency)` (utils) — ніколи literal `$` в лейблах одиниць.

| `nextCopyName` / `bulkCreateNames` | інкремент хвостового числа зі збереженням нулів, пропуск зайнятих |
| `snapshot.ts` (`readSnapshot`/`writeSnapshot`) | SWR-кеш списків: малюємо з localStorage миттєво, оновлюємо тихо; ключі per-user, TTL 24h. Скелетон — лише коли реально нічого малювати |
| `image.ts` (`compressImage`) | стиснення фото до ≤1920px JPEG перед аплоудом; **fail-open** — будь-який збій повертає оригінал |
| `updateProperty(id, payload, { optimistic, silent })` | optimistic-мутації з відкатом; патерн undo-тоста: `showToast({ actionLabel: 'Скасувати', onAction })` |
| `formatPrice(amount, cur)` | ЄДИНИЙ грошовий форматер, тож він невибухаючий: нескінченне/NaN → «—». `undefined.toLocaleString` кидав і забирав екран у ErrorBoundary, NaN друкував «$NaN» просто в картку. Гарди на місцях виклику лишаються — це остання сітка, не дозвіл передавати сюди що завгодно |
| `calcRent` / `monthlyRent` | невідома ставка = НУЛЬ, не NaN. Сирий NaN їхав у компаратор сортування «за орендою» (будь-яке порівняння з NaN дає false → довільний порядок) і в агрегати: один паркінг без добової ставки робив NaN **увесь** дохід дашборда. У `monthlyRent` гілка `per_day` не йде через `calcRent`, тож гард потрібен в обох |
| `matchesQuery(q, ...fields)` | ЄДИНИЙ шлях для пошуку в списках. Токени по пробілах, кожен мусить зустрітись у будь-якому полі — тож «офіс мале» знаходить «Офіс 10 поверху ( мале крило )», де точного підрядка немає. Порожній запит пропускає все. НЕ писати `name.toLowerCase().includes(q)`: одне поле + точний підрядок і був баг «пошук не підтягує нічого» |
| `searchPattern(q)` | найдовший токен для серверного `ilike` (звужує вибірку), повний збіг доганяє `matchesQuery` на клієнті. Вирізає `,()*` — інакше назва з дужками ламає синтаксис `or=(...)` PostgREST |

## Native Telegram chrome

- Хедер/фон/нижній бар — ЗАВЖДИ `#06050e` (верх усіх `.bg-*` градієнтів), незалежно від теми Telegram (застосунок темний; світла тема давала білі смуги). Ставиться в `layout.tsx`.
- **Нижньої смуги Telegram (`MainButton`/`SecondaryButton`) в застосунку НЕМА —
  прибрана за рішенням власника (нижній тулбар не подобався), `useMainButton`
  видалений. Не повертай її «бо так у гайдлайнах»: первинна дія — наша пігулка
  `.mbtn`. `native-client-sweep`/`native-confirm` тримають це інваріантом —
  смуга мусить лишатись невидимою НАВІТЬ коли клієнт її пропонує.**
- Всі виклики нових API Telegram (`setBottomBarColor`, `setParams`) — через `?.`
  (старі клієнти і тест-стаби).
- **Незворотні дії підтверджує `confirmAction()` з `lib/confirm.ts`, а не власна модалка.** Нативний `showPopup` несе авторитет платформи (видно, що питає Telegram, а не скрипт у webview); фолбек — `ConfirmHost` у `layout.tsx` з ТИМ САМИМ текстом, тож формулювання не розходяться між платформами. Повертає `Promise<boolean>`; патерн виклику — `const ok = await confirmAction({...}); if (!ok || offlineGuard()) return`. **Порядок важливий:** гард офлайну ПІСЛЯ підтвердження, інакше користувач бачить тост про офлайн, ще нічого не підтвердивши. Свайп-закриття попапа віддає `null` → трактується як відмова. НЕ для підтверджень із введенням: нативний попап має лише кнопки, тож видалення акаунта (набір слова «ВИДАЛИТИ») свідомо лишається на власній модалці.
- **Тема: застосунок ТЕМНИЙ, і це рішення, а не недогляд.** `themeParams` свідомо
  не застосовуються (світла тема давала білі смуги під нативним хромом, а вся
  мова інтерфейсу — темне скло). `data-tg-theme` на `<html>` ставиться лише як
  діагностичний слід «яку тему повідомив клієнт»; **жоден CSS його не читає і не
  має читати** — скоупнутий світлий блок уже колись перефарбовував текст у чорний
  (див. Audit playbook §2).
- **`color-scheme: dark` у `:root` — те, ЧИМ ми про це кажемо ПЛАТФОРМІ.**
  Рішення «застосунок темний» жило лише в наших кольорах, а системі ми його не
  повідомляли — і вона малювала **світлу клавіатуру** поверх темного скла:
  яскрава плита з різким швом по краю замість напівпрозорого шару, крізь який
  видно фон. Скріншот власника (серпень 2026) — саме про це. Заодно темними
  стають нативні поповери (`date`, `select`), які інакше білі.
  **Чого це НЕ дає:** прозорості «як у App Store». Там контент лежить ПІД
  клавіатурою і просвічує крізь неї; у нас Telegram стискає webview, тож під
  клавіатурою нашого контенту фізично немає — блюриться те, що малює сам
  Telegram. `color-scheme` прибирає світло-темний шов, а не цю різницю.
  Гард: `inputs.spec.ts` → «тап по полю НЕ малює кільце…» (перевіряє і схему).
- **Safe area: `max(env(), --tg-safe-*)`, ніколи тільки `env()`.** У webview
  Telegram на iOS `env(safe-area-inset-*)` не наповнюється (Telegram-iOS #1377),
  тому Bot API 8.0 і дав `safeAreaInset` (виріз пристрою) та
  `contentSafeAreaInset` (власні контроли Telegram, напр. шапка у fullscreen).
  `telegramSafeArea()` у `lib/telegram.ts` **складає обидва** — вони про різне, і
  обійти треба кожен; `page.tsx` пише результат у `--tg-safe-top/bottom` і
  перечитує на `safeAreaChanged` / `contentSafeAreaChanged` / `fullscreenChanged`
  / `viewportChanged`. Будь-який новий елемент хрому позиціонується від
  `var(--safe-bottom)`/`var(--safe-top)`, а не від нуля: на них уже висять таббар,
  `.fbtn`, `.batchbar`, тост, кнопки шита. Фолбек саме `0px`, не `0` — у `calc()`
  до довжини не можна додати безрозмірний нуль, декларація стала б невалідною.
  Тести: `safe-area.spec.ts` (Chromium дає env(), тож телеграмний шлях
  перевіряється лише через стаб `__tgSafeArea`).
- **Кожне поле вводу має `aria-label`.** Підпис у сусідньому `.fr-l`/`.fld-l`
  програмно НЕ звʼязаний, тож без aria-label читалка озвучувала поле
  плейсхолдером — ставка оренди читалась як «18», площа як «47». Плейсхолдер
  іменем не вважається. Guard: `a11y-labels.spec.ts` обходить екрани й модалки і
  падає на будь-якому полі, кнопці-іконці чи `<img>` без доступної назви.

### Персонаж «немає фото» — скляна сфера з LED-екраном (`SpaceOrb`)

`src/components/ui/SpaceOrb.tsx` замінив ізометричний будинок (`Building3D`
видалений). Референс власника — GIF: темна скляна сфера, всередині світиться
LED-екран, на ньому очі, що змінюють вираз, згори злітають дрібні частинки.

**Головне спостереження з покадрового розбору референсу, від якого залежить уся
реалізація: сітка «пікселів» СТОЇТЬ, а перелив кольору йде ПІД нею.** Тому
кольорові плями — окремі шари з `translate3d`, а сітка — статичний
`background-image` поверх них. Анімувати сам градієнт (`background-position`)
означало б перемальовувати екран щокадру; `translate3d` композитор робить
безкоштовно, а візуально це той самий ефект.

**Шари по глибині** (перспектива на СЦЕНІ, нахил на внутрішній обгортці —
якщо крутити той самий елемент, що несе перспективу, точка сходу їде з ним і
обʼєм зникає): ореол −60, тіло 0, екран +10, очі +14, пил +40.

**Тіло — БУЛЬБАШКА, а не темна куля** (пряма вимога власника). Три накладені
`radial-gradient`: відблиск згори-зліва, відбите холодне світло знизу і саме
тіло, чия непрозорість іде `.30 → .44 → .58` від центру до краю. Тобто
щільність РАДІАЛЬНА — той самий прийом, що й у первинної кнопки: у центрі
достатньо ґрунту, щоб екран читався, до країв видно фон. `backdrop-filter`
немає ніде: блюр на поверхні, що рухається щокадру, — рівно та патологія
WebKit, через яку його вимикають у шитах і акордеоні.

**Екран має радіальну маску** (`-webkit-mask-image`, суцільний до 52% і
прозорий до краю) — інакше прямокутник LED-панелі різав силует сфери видимим
кантом. Той самий урок, що з полиском на будинку: окремий прямокутник поверх
сцени вилазить за силует ЗА ПОБУДОВОЮ, і лікується це не розміром, а
обмеженням форми.

**Очі — три стани:** спокій (дві вертикальні смужки), блимання за ВИПАДКОВИМ
інтервалом 2.6–6.2 с (рівний ритм читається як індикатор, а не як живі очі) і
примружування на тап разом зі спалахом пилу. Погляд ведеться за пальцем через
ті самі `--nx`/`--ny`.

**Палітра за статусом — це РІЗНІ персонажі, а не перефарбована копія**
(`PALETTE` у компоненті): вільно — бірюза→фіолет із зеленим ореолом, зайнято —
бурштин→рожевий, продаж — синь→фіолет. Тон ореолу узгоджений з бейджем
`STATUS_COLORS` над самою ілюстрацією.

**Порожній герой НЕ має скриму.** `.obj-hero::after` (`transparent →
rgba(0,0,0,.55)`) існує рівно для того, щоб бейдж і назва читались ПОВЕРХ
ФОТО; без фото він лишав темну смугу внизу і рвав перехід у контент — саме це
власник побачив на пристрої. `.obj-hero.empty` знімає і скрим, і власний фон
із блюром, тож градієнт екрана йде крізь героя суцільно.

`will-change` вмикається лише поки палець на сцені (клас `orb-live`), а
`prefers-reduced-motion` читається В JS: CSS-блок не спиняє ні rAF, ні
інлайновий transform — та сама пастка, що вже описана в `Collapsible`.
`transition` на нахилі стоїть тільки для ПОВЕРНЕННЯ: поки палець веде, він
знімається, інакше сцена тягнеться із запізненням і жест читається як
«залипає».

**Гарди — `orb.spec.ts`** (усі falsification-проведені): сцена реально бачить
рух пальця (`--nx`/`--ny` міняються, очі зміщуються), тап дає спалах пилу і
два примружені ока, палітра `free` ≠ `occupied`, порожній герой без скриму й
без власного фону. **Пастка, вже наступана:** гард палітри спершу відкривав
два статуси на ОДНІЙ сторінці — `page.route` реєструється на сторінку, і
повторний `setupApp` мовчки лишає перші фікстури, тож другий статус не доїжджав
до екрана. Кожен статус тепер у власному контексті.

## Design system quick reference

**Фон екрану:** `.bg-blue` (бази/об'єкти), `.bg-purple` (колекції), `.bg-teal` (сповіщення/профіль), `.bg-green` (успіх), `.bg-pink` (share/analytics)

**Скло:** `.glass-s` (картки списків), `.glass` (модальне, акцентні блоки), `.glass-d` (FAB, важливі кнопки)

**Типографіка:** `--fs-sub` (15px) — основний текст рядків; `--fs-cap1` (12px) — підписи; `--fs-cap2` (11px) — мітки uppercase; `--fs-foot` (13px) — допоміжний текст

**Відступи:** `--pad-card` (14px) всередині карток; `--g2` (8px) — gap між елементами; `12px` — зовнішній margin карток від країв

**Іконки — одна бібліотека, одна база, одна шкала** (`src/components/Icons.tsx`,
guard: `tests/unit/icon-system.test.ts`):

- Кожна іконка — `<Icon>…</Icon>` (обведення, лінійні закінчення, viewBox 24 —
  звідти). Власний `<svg>` дозволений лише ілюстраціям, графікам та індикаторам
  прогресу; для іконки це завжди помилка. Раніше так розповзлись чотири іконки
  з іншою геометрією, окремий набір на дашборді і рукописні галочки на екранах.
- Товщина обведення НЕ пишеться руками: `strokeFor(size)` дає 2px до 24px і
  1.7px від 24px (оптична вага). Виняток — `strokeWidth="0"` на залитих гліфах.
- Розміри лише парні, зі шкали **12 / 14 / 16 / 18 / 20 / 24 / 26**
  (+32/34/40 для `Glass*`-гліфів): 2px обведення на непарному боксі дає
  півпіксельні краї. Метадані рядка — `size={14}`, іконка рядка форми/списку —
  `16`, дія в хедері — `20`, таббар — `26`.
- Кольорова плитка під іконкою (дашборд) бере іконку з бібліотеки, а не малює
  свій шлях.

Колір іконок у метаданих (`.obj-mt`): `var(--t3)` для неактивних, `var(--t2)`
для активних.

**Кнопки:** `.btn-glass` + тон `ok|err|info` — усі дії застосунку (плаваюча
`.fbtn` «Здати в оренду»/«Звільнити об'єкт», первинна і небезпечна в модалках):
напівпрозорий тонований шар, блюр, верхній відблиск, кольорове світіння.
Неактивна — нейтральне скло, НЕ `opacity:.45` (над темним шитом кнопка зникала).
Правило порядку в CSS: блок `.btn-glass` мусить іти ПІСЛЯ `.modal-btn`, інакше
`.modal-btn:disabled` перебиває його за однакової специфічності.
`.mbtn` — первинна дія екрана: та сама скляна пігулка (46px, `--r-pill`), що й
`.fbtn`. Суцільною смугою вона була, поки лишалась DOM-двійником непрозорої
нативної MainButton; та кнопка прибрана, тож причина зникла разом із нею.
Відрізняється від `.fbtn` одним: піднімається над клавіатурою (`--keyboard-h`),
бо стоїть на екранах вводу. `mbtn-flow` — той самий вигляд, але в потоці
(форми; див. Form & input rules про війну плаваючої кнопки з полями).
`.obj-act-btn` — дії всередині картки; `.hdr-a` — дія в хедері (44×44)

**Родина первинних дій має ОДИН розмір і ОДИН натиск — це рішення власника,
а не наслідок.** Було два габарити: 52px/`min-width:200` у плаваючої дії екрана
деталі («Звільнити обʼєкт») проти 46px у решти. Кожен мав пояснення («там
кнопка і є головна дія»), але на сусідніх екранах різниця читалась як
недбалість. Тепер уся родина — 46px / `padding:0 24px` / `--fs-foot` /
`--r-pill`; `.fbtn.compact` лишився РОЗМІТКОВИМ маркером і геометрії не міняє.
Гард — `design-system-runtime.spec.ts` («первинна дія — ОДИН розмір»), і він
міряє РЕНДЕР, а не CSS: екрани вже ламали геометрію інлайновим стилем.

Натиск теж один на всю родину (`scale(.96)`), із **асиметричними
тривалостями**: втискається за `--dur-xs`, відпускається за `--dur-sm` — рівні
.12s з обох боків читались як клац. **`filter:brightness(1.1)` на натиску
прибрано СВІДОМО:** фільтр діє й на результат `backdrop-filter`, тобто освітлює
ґрунт під білим підписом — той самий важіль, який заради читабельності крутять
у зворотний бік (див. нижче).

**Заливка первинної кнопки — це КОНТРАСТНЕ обмеження, не смак.** Білий підпис
вимагає ґрунту з `L ≤ 0.183` (звідти 4.5:1). Фірмова синя цього не дає НІКОЛИ:
`#2AABEE` має `L=0.357`, тобто **3.02:1 навіть суцільна, без прозорості** —
підняттям альфи задача не розвʼязується в принципі, кнопка лише перестала б бути
склом. Тому заливка бере `--blue-deep` (#16719E, `L=0.145` → 5.4:1), рівно як
`--pink-deep` колись завели для «Створити базу». Три речі, які тут працюють
разом, і жодну не можна прибрати поодинці:
1. **`backdrop-filter: brightness(.6)`** — головний важіль, і раніше він стояв
   ПРОТИ мети (`1.06` освітлював ґрунт під кнопкою). Затемнювати треба backdrop,
   а не піднімати альфу: щоб узяти поріг альфою, знадобилось би ~0.9.
2. **Градієнт щільніший ДОНИЗУ** (`.74 → .79`, а не навпаки): градієнт екрана
   світлішає донизу, тож саме нижній край пігулки лежить на найсвітлішому.
   Попередній рецепт мав слабший стоп саме там, де найважче. **Стеля жорстка:
   обидва стопи мусять лишатись НИЖЧЕ 0.8** — це інваріант `modals.spec.ts`
   («жоден стоп не суцільний»), і він законний: застосунок збудований на склі.
   Спроба взяти поріг альфою .92 на нього й напоролась.
3. **Неактивна бере `--glass-off`** (темний `rgba(6,5,14,.62)`), а не
   `--glass-2`: та біла плівка ОСВІТЛЮВАЛА і давала 2.77:1. Правило «неактивність
   показує колір, а не `opacity`» лишається — просто колір темніший.
Зелений `.success` і рожевий `.pink` поріг проходять і НЕ чіпались, але запас у
зеленого нульовий: `#34C759` — це 2.22:1 при повній заливці, тобто він тримається
виключно тим, що стоїть вище в градієнті. Пересунете зелену CTA нижче — впаде.

**Скло проти заливки: щільність РАДІАЛЬНА, і це не косметика.** Власник
сказав, що кнопка «просто закрашена кольором» і прозорості не видно — і мав
рацію, хоч альфа справді була знижена. Винен був не тон, а
`backdrop-filter: brightness(.42)`: він рівномірно гасив УСЕ за кнопкою, тож
дивитись крізь скло не було на що, і лінзування при прокрутці не читалось.
Тепер щільність залежить від місця: `.74` у центрі, де лежить білий підпис (і
де зонд міряє контраст), `.16` до країв, де око читає скло. Край став утричі
прозорішим за попередній рівномірний `.47`.
**Заміряна драбина на найгіршому місці («Завантажити PDF»), 4 ітерації:**

| рецепт | контраст |
|---|---|
| рівномірна `.44/.47` + backdrop `.42` | 4.79 |
| радіальна `.60→.16` + backdrop `.62` | **4.21** |
| радіальна `.74→.16` + backdrop `.62` | **4.32** |
| радіальна `.74→.16` + backdrop `.52` | ✓ поріг узято |

Головний висновок числами: ущільнення заливки дало **0.11**, а backdrop —
**0.4**. Тобто скільки скла можна показати, визначає саме backdrop, і межа
знизу фізична: білий підпис мусить читатись на найсвітлішому екрані.
Не «оптимізуйте» це назад у рівномірний градієнт — виграшу в контрасті він не
дає, а скло вбиває.

**Прозорість підняли на 40% (рішення власника, серпень 2026) — і саме тому
важіль brightness виявився не «одним із трьох», а НЕСУЧИМ.** Альфи всіх тонів
×0.6: синій `.74/.79 → .44/.47`, зелений і червоний `.52/.34 → .31/.20`,
рожевий `.58/.38 → .35/.23`. Замір показав, що ціна рівно **0.39 контрасту**:
«Завантажити PDF» пішов 4.79 → **4.40** при порозі 4.5, тобто розійшлось на
0.1, а не принципово. Різницю добрано затемненням `brightness .5 → .42` —
прозорість лишилась тією, яку просили. Урок той самий, лише з іншого боку:
**прозорість і контраст тут керуються РІЗНИМИ ручками**, тож «стало прозоріше»
не мусить означати «стало гірше видно» — доки є запас у backdrop. Запас цей не
безкінечний: далі скло почне читатись як темна плашка.

**Радіуси — ПРАВИЛО, а не набір чисел.** Шкала контейнерів: 8 / 12 / 16 / 20 /
24 / пігулка. Проміжних значень у ній свідомо немає, бо вкладений елемент не
обирає собі число, а ВИВОДИТЬ його: `--rc-in` = `--rc-out` − `--rc-pad`, тобто
радіус батька мінус відступ між ними. Це принцип концентричності, який Apple у
iOS 26 винесла в окрему фігуру `ConcentricRectangle`: дуги батька й дитини
мусять мати спільний центр, інакше кути читаються як дві різні системи.

```css
батько { --rc-out:var(--r-sm); border-radius:var(--rc-out); padding:var(--rc-pad) }
дитина { border-radius:var(--rc-in) }   /* 12 − 2 = 10, тримається саме */
```

Префікс `rc-`, а не `r-`, навмисно: гард шкали парсить `--r-*` і брав би
службовий відступ за легальний радіус контейнера. Модалка має іменований
`--r-sheet` (=`--r-xl`, 24px — аркуші iOS 26 помітно круглі).

**Гард перевіряє РІВНЯННЯ, а не список винятків** (`design-system-runtime`):
читає радіус і падінг БАТЬКА і дозволяє дитині рівно `батько − падінг`, за
умови що батьківський радіус сам зі шкали. Доти там жив перелік («9px на
`.view-seg-b` — можна»), і саме він ховав дрейф: перемикач «Поточні/Архів» у
календарі мав 12/10 при падінгу 3, тобто МАЙЖЕ концентрику з розходженням 1px.
Виправлення — не підгонка числа, а переведення на спільні `.seg`/`.seg-b`.

**Сегмент фільтра — 34px і 11px** (рішення власника про компактніше меню).
Це свідомо нижче 44px: власний `overflow:hidden` під ellipsis клiпає будь-який
`::after`, тож підняти зону дотику, не піднявши бокс, тут неможливо. У
`TAP_DEBT` із причиною; прецедент — `UISegmentedControl` Apple має 32pt, а
смуга розтягнута на всю ширину.

**Форми:** `.fg` (контейнер секції), `.fr` (рядок 48px з border-bottom), `.fr-l` (лейбл), `.fr-i` (input 16px щоб iOS не зумив)

**Правило:** не використовувати `rgba(...)` inline — брати токен (`var(--glass-2)`, `var(--t3)` тощо). Інлайн `style={{}}` тільки для динамічних значень (розраховані ширини, умовні трансформи).

**Шари — шкала `--z-*`, сирий `z-index` заборонений** (гард
`design-tokens.test.ts`, рантайм — `layering.spec.ts`). Було 19 різних сирих
чисел у CSS + 7 інлайном; прочитати їх було неможливо навіть уважно, бо число
осмислене лише ВІДНОСНО інших. Шкала має **два яруси, і порівнювати числа МІЖ
ними безглуздо**: до `--z-overlay` — усе, що живе всередині `#app-root`; від
нього — портали в `<body>`. Причина: `#app-root` має `position:fixed`, а
фіксований елемент у Chromium створює контекст накладання (див.
`layering.spec.ts` про спростовану гіпотезу з `.batchbar`). Зростання шкали
збережене просто щоб файл читався чесно.

**Тінь: рецепт, написаний УТРЕТЄ, — це токен** (`--shadow-glass-btn`,
`--shadow-glass-btn-danger`, `--shadow-glass-off`, `--shadow-seg-on`). НЕ «кожна
`box-shadow` має бути токеном»: із 46 літералів більшість — власна графіка
правила (фокус-кільце, світіння, inset-смуга сповіщення), і токенізувати їх
означало б вигадати систему там, де її нема. Родина починається з третього
входження — і саме там дрейф невидимий: `.view-seg-b.on` мав
`rgba(255,255,255,.28)` там, де три його брати-сегменти мали `.3`.

**Клавіатурний фокус: блок `:focus-visible` мусить іти ОСТАННІМ у globals.css.**
Порядок не стилістичний, а єдине, що робить правила живими. `input:focus-visible`
існував і виглядав як робоче кільце — але кожне СПРАВЖНЄ поле стилізоване класом
(`.fr-i`, `.fld input`, `.search-inline input`, `.fold-mng-input`,
`.fr-textarea`), а клас перебиває селектор за типом, тобто `outline:none` із них
гасив кільце всюди, де воно мало значення. Не-поля (кнопки, `.sheet-row`,
сегменти, таббар) кільця не мали взагалі — тобто фікс `modal-a11y` («Tab доходить
до рядків шита») працював усліпу. Контролам, що клiпають себе самі
(`overflow:hidden` під ellipsis), потрібен `outline-offset:-2px` — зовнішнє
кільце там обрізалось би, як колись `::after`. Гард — `modal-a11y.spec.ts`, і він
вимагає **≥2px**: без нашого правила Chromium малює власну волосинку
`outline:auto 1px`, на якій поріг «>0» проходив би вакуумно.

**Нерозривний рядок: носії імен мають `overflow-wrap:anywhere`**
(`.row-s,.row-t,.obj-t,.obj-mt,.fr-l,.notif-t,.notif-s,.dash-l`). Захист був
рівно один — `.link-mono` — тобто назва бази, обʼєкта, орендаря й папки не мали
жодного, а користувач вставляє з буфера саме таке: посилання, e-mail,
кадастровий номер. Саме `anywhere`, а не `break-word`: лише він зменшує
min-content розмір, тож діє і на флекс-елемент. **Супутня пастка, знайдена тією
ж фікстурою:** `.row-t` перевизначено інлайновим `display:flex`, що вимикає
успадкований `text-overflow`, а флекс-елемент за замовчуванням має
`min-width:auto` — тобто відмовляється стискатись нижче max-content. Назва без
пробілів через це вилазила за екран на **37px**, і ellipsis у компактному рядку
не спрацьовував НІКОЛИ. Лікується `minWidth: 0` на носії тексту. Гард —
фікстура `UNBREAKABLE` в `ui-audit.spec.ts`.

## Audit playbook

This repo gets audited in four recurring flavors. Each has its own checklist and gotchas learned the hard way across past sessions — check these before assuming a finding is new.

### 1. DevSecOps / security audit

Run every Edge Function and RLS policy touched through the OWASP Top-10 checklist and Security rules above. Recurring findings to check for specifically:
- Rate limiter fails open instead of closed (must reject on lookup failure, not allow through)
- `tg_id` passed as a string to a BIGINT column (must `parseInt(tgUser.id, 10)`)
- Edge Function error responses leaking stack traces or `detail` fields to the client
- Storage paths containing user-controlled segments instead of `{propertyId}/{timestamp}_{rand}.{ext}`
- New tables missing `ALTER TABLE … ENABLE ROW LEVEL SECURITY`

### 2. UI/UX & design-system audit

Triggered by reports like "text/buttons are black", "gradient disappeared", "icon should be a different color". Walk every screen in `src/screens/` against the Design system quick reference above. Known root causes from past audits — rule these out before touching new code:

- **Duplicate CSS variable definitions.** `--t1`/`--t2`/`--t3`/`--t4` (and other design tokens) must be defined exactly once, in `:root` in `globals.css`. A scoped block like `[data-tg-theme="light"] #app-root{--t1:#1a1a1a;...}` or a stray `.light-page{...}` class silently overrides text color to dark even when no component renders that class. Sanity check: `grep "  --t1:" src/app/globals.css` must return exactly one line. This exact bug recurred across a revert + a PR merge — re-check after any merge into the design CSS.
- **Pseudo-element overlays carry gradients/shadows, not the base class.** `.hdr`, `.tabbar`, etc. have no background of their own by design (bare-icon aesthetic) — gradient scrims and specular highlights live in `::before`/`::after`. When a "gradient disappeared" or "shadow behind icons" report comes in, grep for `::before`/`::after` on that selector before editing the base rule, and check `git log -S".selector::before"` to see if it was stripped in an earlier redesign.
- **Screen backgrounds must use a `.bg-*` gradient class** (`.bg-purple`, `.bg-welcome`, `.bg-teal`, etc.), never an inline flat color or a `var(--tg-theme-*-bg-color, #hex)` fallback. The Telegram theme var is a single flat color and reads as "gradient missing" the moment Telegram doesn't inject it (outside Telegram, or before the SDK finishes loading on a cold start) — this is exactly what happened to `SplashScreen`.
- **Money/currency figures and the dollar icon are green** (`var(--ok)` / `var(--ok-fg)` / `var(--ok-bg)` / `var(--ok-bd)`), not amber. Standardized across `DatabaseListScreen`, `DatabaseObjectsScreen`, `PropertyDetailScreen`, `PropertyFormScreen`, `PaymentCalendarScreen` — don't reintroduce `#c2820a` or `#fbbf24` for currency display (those amber tones stay reserved for non-money things like electricity/bolt icons and pending-status badges).
- **No inline `rgba(...)`.** If a color repeats with no existing token, that's a signal a new semantic token belongs in `:root`, not another inline literal.

### 3. Full-workflow verification (auth → CRUD → upload → UI)

This sandboxed environment has **no outbound network** to Vercel/Supabase preview URLs (403 host-not-in-allowlist), але Playwright Chromium ПРАЦЮЄ (`/opt/pw-browsers`) — 57+ e2e ганяються локально проти статичної збірки з герметичним мок-бекендом (`tests/e2e/helpers/harness.ts`). Verify changes by:
1. `npm run type-check && npm run lint && npm run test && npm run build && npx playwright test` — все має бути зелене.
2. Inspect the compiled output directly: `grep` the generated `out/_next/static/css/*.css` and `out/_next/static/chunks/**/*.js` for the literal class names/color values you changed. CSS gets minified and `::before`/`::after` rules get merged onto shared selectors — search for the property value (e.g. a hex color or class name string), not the exact original selector text.
3. State explicitly to the user that this substitutes for live browser/Vercel verification, since neither is reachable from this environment.
4. **Прод перевіряється через API** (мережа до GitHub/Vercel MCP є, до самих хостів — ні): статус workflow-ранів на merge-коміті (`deploy-edge-function.yml` — success?) і Vercel-деплой merge-коміту (`target: production`, `state: READY`). Порівняй sha деплою з `origin/main`.

### 4. Глибокий bug-hunt (коли просять «перевір, щоб багів не було»)

Процес, який у липні 2026 знайшов 8 реальних багів за чотири раунди:

1. **Воркфлоу ролей наскрізно** — не окремі екрани, а вхідні ланцюги: deep link → клейм/підписка → лендинг → CRUD. Всі п'ять префіксів (`guest_/db_/prop_/col_/team_`) мають e2e; новий вид лінка = новий тест У ТОЙ ЖЕ ПР.
2. **Довгі ланцюги, які поодинокі тести не проходять** — платіжний цикл цілком, аплоуд з підрахунком запитів, аварійні режими (403 від RLS, офлайн-гард, відновлення).
3. **Багатокутовий code-review дифу** — 8 паралельних finder-кутів (порядковий скан, видалена поведінка, крос-файловий трасер, reuse/спрощення/ефективність/altitude/конвенції) → дедуплікація → верифікація КОЖНОГО кандидата з цитатами коду (CONFIRMED/PLAUSIBLE/REFUTED). Найкращі знахідки дає скан незмінених рядків у зачеплених функціях.
4. **Пошук класу знайденого бага** — після кожного фікса грепни той самий патерн скрізь: один інстанс класу майже ніколи не єдиний.

**Класи багів, які тут уже ловили** (перевіряй нові входження):
- **Мутація в mount-ефекті без гарда** — StrictMode у dev проганяє ефекти двічі → дабл-INSERT/аплоуд. Гард: `startedRef` (ref переживає double-invoke). Легальні альтернативи: серверний дедуп (`record_public_view` 1/хв), виклик із event handler (не з ефекту).
- **Інлайн-копії спискових констант** — список deep-link-префіксів жив 4 копіями і розійшовся (team_ був пропущений скрізь). Єдине джерело: `isDeepLinkStartParam()` у `lib/telegram.ts`. Відомий залишок боргу: диспетчер `useDeepLink` і no-session гілка Splash (slice-офсети) досі тримають власні копії — кандидат на `parseStartParam()`.
- **Екран бере дані ТІЛЬКИ зі стору** — стор наповнює інший екран, тож прямий вхід (deep link) на холодному старті = вічний спінер. Self-contained правило: екран, що вміє бути точкою входу, довантажує свій рядок сам (одиночний select за id — RLS вирішує видимість для будь-якої ролі; `loadDatabases` фільтрує по owner+membership і чужі бази не поверне).
- **`?.` на Telegram API = мовчазний no-op поза Telegram** — кнопка виглядає живою і нічого не робить. Кожен такий виклик потребує фолбека (`openTelegramShare` → `window.open`) або DOM-фолбека (MainButton → `.mbtn`).
- **Дії, що скасовують ефект безпекової операції** — revoke ставить `share_expires_at=now()`, але токен ЛИШАЄТЬСЯ: будь-який `set_expiry`/`clear_expiry` оживляє відкликаний лінк для всіх, хто його зберіг. Реактивація мертвого лінка — тільки через явне підтвердження. Перевіряй цей патерн для нових «м'яких» відкликань.
- **`opts.silent` має глушити ВСІ тости шляху** — і офлайн-гард, і catch, не лише success (фонова операція не має лякати користувача, який нічого не робив).
- Відомий борг (задокументовано в PR #39): дубльований конвеєр аплоуду `PhotoUploadScreen` vs `useProperties.uploadPhoto` (вже розійшлись: queueIdx у шляху, sort_order) — уніфікувати при наступному дотику.

### 0g. Видалення акаунта (delete_my_account) — виконати SQL в Dashboard → SQL Editor

Файл: `supabase/migrations/044_delete_account.sql`.

RPC `delete_my_account()` (SECURITY DEFINER, лише `authenticated`) — самостійне
стирання акаунта, обіцяне в Політиці конфіденційності §5.

**42P13 при повторному застосуванні:** `CREATE OR REPLACE` не змінює тип
результату наявної функції. Міграція тому починається з `DO`-блоку, що дропає
ВСІ перевантаження `public.delete_my_account` за іменем (через
`oid::regprocedure`), і лише потім робить `CREATE`. Той самий патерн потрібен
будь-якій міграції, що переоголошує `RETURNS TABLE` (пор. явний
`DROP FUNCTION IF EXISTS get_public_property_preview(TEXT)` у 042).

**Нюанс порядку, який ламав би DELETE:** майже все каскадить від `users(id)`,
АЛЕ `property_views.viewer_id` оголошений БЕЗ `ON DELETE` (тобто NO ACTION), і
одна переглядова позначка заблокувала б видалення. RPC спершу знеособлює її
(`viewer_id = NULL`), відвʼязує гостьові лінки й членства в чужих командах, і
лише тоді видаляє `public.users` (каскад) + рядок у `auth.users` (без цього
наступний вхід із того ж Telegram підняв би сесію на порожній профіль).

Файли зі storage прибирає КЛІЄНТ (`useAuth.deleteAccount`) ДО виклику RPC —
після каскаду шляхи вже недоступні. Осиротілий файл не є витоком: політики
читання прив'язані до рядків, яких уже немає.

UI: `ProfileScreen` → «Видалити акаунт» (приглушений стиль, щоб не запрошував до
тапу) → модалка з **типізованим підтвердженням**: кнопка активна, лише коли
вписано `ВИДАЛИТИ`. Без міграції кнопка є, але RPC поверне помилку — тост
«Не вдалося видалити акаунт», користувач лишається в акаунті.

воно БІЛЬШЕ (напр. під час стиснення клавіатурою).

## Changelog — тестування дизайну (серпень 2026)

Запит: **план тестування дизайну**. Дизайн тут уже покритий щільно (18 e2e-спеків
+ 2 юніт-гарди), тож роботою було не «додати тести», а знайти те, чого не бачить
жоден із наявних — і кожну прогалину виміряти числом, а не оголосити.

**Знайдено й виправлено (усі falsification-проведені):**
- **Дрейф тіні на четвертому сегменті.** `.seg-b.on`, `.fr-seg-b.on`,
  `.notif-tab.on` мали один рецепт, `.view-seg-b.on` — `rgba(255,255,255,.28)`

- **Кільце фокуса не працювало НІДЕ.** `input:focus-visible` існував, але кожне
  справжнє поле стилізоване класом із `outline:none`, а клас перебиває тип; не-поля
  кільця не мали взагалі. Тобто фікс `modal-a11y` («Tab доходить до рядків шита»)
  лишав користувача навігувати всліпу.
- **Назва без пробілів вилазила за екран на 37px** у компактному рядку, і
  ellipsis там не спрацьовував НІКОЛИ (`display:flex` інлайном + флексовий

- **Дві сліпі зони зонда тап-таргетів**, через які він репортував неіснуючі
  дефекти («висота 1px»): `pointer-events:none` у неактивних контролів і чіп,

екранами; тепер обидва ходять 21-м через спільний `helpers/screens.ts`. Це

## Changelog — первинна кнопка над WCAG AA (серпень 2026)

Єдиний борг, який аудит дизайну свідомо лишив власнику: `.mbtn` — ПЕРВИННА
кнопка застосунку — була нижче AA на пʼятьох екранах (2.35:1 на «Завантажити
PDF», 2.77 на неактивній «Продовжити →», 3.14 / 3.25 / 4.09 на решті). Власник
сказав робити.

**Головне, що зʼясував рахунок ПЕРЕД правкою: альфою це не лікується.** Відносна
яскравість самих відтінків за WCAG-формулою — `#2AABEE` 0.357, `#229ED9` 0.298,
`#C42378` 0.143, `#34C759` 0.423. Тобто фірмова синя не бере поріг **навіть
суцільна**: 3.02:1. Щільніша заливка тим самим кольором зробила б кнопку
непрозорою, лишивши текст нечитабельним. Потрібен глибший відтінок — рівно те,
що вже одного разу зробили для «Створити базу» через `--pink-deep`.

**Три важелі, знайдені ітеративним заміром** (кожен крок — прогін `contrast` на
21 екрані, а не арифметика): `--blue-deep` як заливка; `backdrop-filter`
`brightness(1.06) → .5` (той, що раніше активно ШКОДИВ); і розворот градієнта
щільнішим донизу, бо саме там ґрунт найсвітліший. Експорт ішов 2.35 → 3.54 →
4.2 → 4.4 → **4.79**: перші два важелі поодинці порогу не брали.

**Стеля, на яку я напоровся, і вона законна.** Проміжна версія брала поріг
альфою .92 — і `modals.spec.ts` («жоден стоп не суцільний», max < 0.8) її
завалив. Правило слушне: застосунок збудований на склі, і суцільна заливка
вибиває кнопку з мови інтерфейсу. Тож обидва стопи лишились під 0.8, а
відсутній контраст добрано затемненням backdrop (.6 → .5). Урок ширший:
контрастний поріг тут НЕ вільна змінна — він живе всередині рамки «лишайся
склом», і саме тому важелем є brightness, а не альфа.

**Результат:** 4.79–8.22:1, `mbtn` прибрано з `CONTRAST_DEBT`, `FROZEN` опущено
на пʼятьох екранах (realtor-dashboard 1→0, realtor-database 6→5,
sharing-analytics 3→2, export 2→1, role-select 1→0). Falsification: повернув
старий градієнт — гард упав саме на `mbtn` (3.16:1).

**Не чіпав свідомо:** зелену й рожеву CTA (поріг проходять) і контраст списку
рієлтора (інший механізм — положення картки в градієнті).

## Changelog — плавність і клавіатура за записом з пристрою (серпень 2026)

Скарги власника: у модалках із полем вводу клавіатура перекриває або піджимає
шит; багато де ривки. До запису екрана обидві були недоказовими — тепер перша
частина заміряна покадрово, і це перша реальна цифра по iOS у цьому проєкті
(інструмент і профіль — у розділі про блюр вище).

**Прибрано переліт зі шкали кривих.** `--ease` виходила на 1.4, `--ease-spr` на
1.56 — тобто елемент пролітав повз своє місце і вертався. На записі це видно
прямо: шит опинявся на 75px ВИЩЕ кінцевої позиції, потім хитався 87 → 95 → 93 →
90. Рішення власника — спокійне сповільнення. Змінено ЗНАЧЕННЯ токенів, а не 74
місця вжитку; назви лишені навмисно (`--ease-spr` більше не пружина, про це є
коментар у `:root`). Гард — «жодна крива не має перельоту вище одиниці».

**Виїзд шита: 380мс пружини → 300мс `--ease-out`**, як в акордеоні.

**Автофокус прибрано з модалок — але не звідусіль, і різниця істотна.**
Спершу я діагностував, що `SheetCreateRow`/`FolderManageModal` фокусують поле
посеред анімації відкриття. **Читання коду це СПРОСТУВАЛО:** у пікерів поле
взагалі не існує до тапу по «+ Нова папка» (`open = !collapsedLabel`), у
керуванні папками `autoFocus` не передається, а рядок перейменування
монтується від тапу. Реально автоматичних фокусів було рівно два — таймери
`setTimeout(…, 400)` в `InviteSheet` і в шиті оренди. Саме їх і прибрано:
затримка була правильна, але не усувала причини — фокус сам підіймає
клавіатуру, а та тягне пробу `kbFallback` (350+200мс) і два паралельні
`transition` геометрії шита. Тап-ініційований фокус лишається: це пряма
відповідь на дію користувача, а не «автоматично».

**Наступним раундом це рішення СКАСОВАНО — див. changelog нижче.** Розрізнення
«таймер = автоматично, тап = ні» було моєю інтерпретацією відповіді власника
(«не фокусувати автоматично взагалі»), і саме воно лишило дефект живим: тап по
«+ Нова папка» МОНТУЄ поле, тобто міняє висоту шита, і фокус у той самий кадр
запускає весь ланцюг вище. Зараз `autoFocus` у шитах немає взагалі.

**Гарди (усі falsification-проведені):** крива без перельоту; `modalSlideUp`
рухає лише `transform`; жоден шит не фокусує поле по таймеру; `.modal` і
`.modal-overlay` не блюрять під час руху і повертають блюр після.

**Урок про власні гарди.** Перша версія перевірки кривих брала з
`cubic-bezier(x1,y1,x2,y2)` індекси 2 і 4 замість 1 і 3. Індекс 4 не існує,
`undefined > 1` завжди false — гард проходив НАВІТЬ із поверненою пружиною.
Спіймано власною ж фальсифікацією: якби я не зламав код навмисно, у наборі
лишився б зелений тест, що не перевіряє нічого.

**Чого це НЕ доводить.** Що на iOS стало плавно. Chromium блюр майже не
коштує, тож CI не побачить ані дефекту, ані фікса — доказом буде лише новий
запис того самого жесту, прогнаний через `scripts/analyze-recording.py`.
Клавіатурний сценарій у записі теж відсутній: діагноз зроблено з коду, і
підтвердить його теж лише запис.

## Changelog — клавіатура в шитах і вартість акордеона (серпень 2026)

Продовження попереднього раунду: там закрили те, що показав запис (стрибок на
старті виїзду шита і переліт пружини), тут — дві частини скарги, яких запис не
торкався.

**`autoFocus` у шитах немає взагалі, і попереднє рішення скасовано.** Минулого
разу я лишив тап-ініційовані автофокуси, розсудивши, що вони «пряма відповідь
на дію». Помилка була в тому, ЩО САМЕ робить тап: він МОНТУЄ поле, тобто міняє
висоту шита — і фокус у той самий кадр додає до цього пробу `kbFallback`
(350+200мс), `padding-bottom .25s` оверлея і `max-height .25s` шита, усе поверх
48px-блюру. Це рівно те, що власник описав словами «відразу клавіатура
перекриває або піджимає». Прибрано з `SheetCreateRow` (разом із мертвим після
цього пропом) і з рядка перейменування `FolderManageModal`. Ціна — один зайвий
тап по полю, прийнята свідомо. Екранні `autoFocus` (`CreateDatabaseScreen`,
`PropertyFormScreen`) НЕ чіпані: там немає ні слайд-анімації шита, ні
клавіатурної корекції оверлея.

**Блюр знято і на час КЛАВІАТУРНОГО руху, не лише на час виїзду.** `moving`
гасне на `animationend` відкриття, а клавіатура рухає геометрію пізніше і
власними переходами — тобто повз нього, і саме ті кадри лишались зі склом.
Доданий `kbMoving` (клас на DOM той самий, щоб наявні очікування
`.modal-overlay.moving → 0` не поламались) зводиться на зміну
`reportedKeyboardPx()` більш ніж на 20px і гасне через 300мс. Поріг
обовʼязковий: пристрій шле висоту кількома тіками (див. тест «шит не СНЕПАЄ між
висотами»), і без нього дрібний хвіст тримав би блюр знятим довше за сам рух.

**Акордеон папок більше не фейдить піддерево.** `Collapsible` гнав `opacity`
разом із `height`, тобто щокадру все піддерево папки (до 24 карток) рендерилось
в офскрін-буфер і композитувалось з альфою — заради переходу, який і так
схований `overflow:hidden`. Тепер рухається лише висота; нуль для згорнутої
секції виставляє хвіст `anim.finished`, тобто у спокої. Заодно прибрано
`will-change:height` з `.fold-wrap`: `height` не композитна властивість, тож
підказка нічого не пришвидшує, зате тримається постійно на кожній обгортці —
те саме правило, через яке її немає на `.nav-wrap` і `.modal`.

**Свідомо НЕ зроблено:** `contain:paint` на `.fold-wrap` (створює контекст
накладання, тобто backdrop root — скло всередині папки перестало б бачити фон
під собою); `shimmer` скелетона і `cmarkPulse` коачмарка (єдині безкінечні
анімації на некомпозитних властивостях — переведення міняє ВИГЛЯД і тягне
перезняття бейслайнів, а замірів по них немає); каскад входу на екран
(`screenEnter` + `cascadeIn` анімують `opacity` на елементах із
`backdrop-filter` — патологія для WebKit, але переписувати мову входу всіх
екранів без заміру не можна).

**Гарди** (усі falsification-проведені): нуль `autoFocus` у компонентах шитів;
блюр знято під час клавіатурного руху і ПОВЕРТАЄТЬСЯ після; обгортка акордеона
не фейдить під час руху. Пастка заміру, вже наступана в цьому ж раунді: клас
вішає РЕНДЕР React, а не сам обробник події, тож `getComputedStyle` у тому ж
`evaluate`, що й `dispatchEvent`, читає стан ДО коміту — перша версія гарда
падала саме на цьому, а не на коді.

## Changelog — клавіатура, фокус і родина CTA (серпень 2026)

Три скріншоти з пристрою: наша форма з відкритою клавіатурою, наш екран
створення бази, і — як зразок — пошук в App Store. Скарги: клавіатура виглядає
чужою («чорна тінь за нею»), синій контур на полі при введенні, і окремо —
підняти прозорість CTA на 40%, звести їх до єдиного розміру й дати гарний
натиск.

**Два дефекти, і другий — мого авторства.**

- **Світлої клавіатури не мало бути.** `color-scheme` не був заданий НІДЕ, тобто
  рішення «застосунок темний» жило лише в наших кольорах, а платформі ми його
  не казали. iOS малював світлу клавіатуру поверх темного скла — звідси і
  «яскрава плита з тінню». Деталі й межа можливого — у Native Telegram chrome.
- **Синє кільце на полі поставив я** раундом раніше, разом із коментарем, що
  «тач кільця не отримує». Твердження хибне для текстових полів: вони матчать
  `:focus-visible` завжди. Тобто помилка була не в CSS, а в переконанні під ним
  — і рівно тому її не спіймав жоден гард: усі вони міряли кнопки, де
  твердження правдиве. Правило — у Form & input rules.

**Родина CTA: прозорість +40% і один розмір.** Ключова цифра — прозорість
коштувала **0.39 контрасту** (4.79 → 4.40 при порозі 4.5), і це добралось
затемненням backdrop, а не поверненням альфи. Тобто вимога власника і WCAG AA
розійшлись на 0.1, а не конфліктували принципово; деталі — у блоці про заливку
первинної кнопки. Розмірів було два (52/46), став один (46). Натиск був
описаний двічі, став один — з асиметричними тривалостями і без
`brightness(1.1)`, який освітлював ґрунт під білим підписом.

**Гарди:** «тап по полю НЕ малює кільце фокуса» (він же перевіряє
`color-scheme`) і «первинна дія — ОДИН розмір на всіх екранах» (міряє РЕНДЕР на
всіх 21 екрані, бо джерельний гард пропустив би інлайнове перевизначення).
Обидва falsification-проведені.

**Чого зробити НЕ вдалось, і це не обійти кодом:** клавіатура не стане
прозорою «як в App Store». Там контент лежить ПІД клавіатурою і просвічує крізь
неї; у нас Telegram стискає webview, тож під клавіатурою нашого контенту
фізично немає. `color-scheme` прибирає світло-темний шов — не цю різницю.

**ПРИЙНЯТИЙ НАСЛІДОК ПРОЗОРОСТІ: зелена кнопка на рожевому екрані читається
БУРОЮ.** Знайдено A/B-порівнянням кадрів (див. нижче) і заміряно по центру
заливки «Створити підбірку»: `#818a73` (відтінок **84°**, зелений) → `#83746b`
(**22°**, бурий). Механізм — рожевий фон проступає крізь ослаблений тон сильніше
за сам тон; синя (192°→178°) і рожева (326°→276°) кнопки відтінок тримають, бо їхній
відтінок близький до фону або сильніший за нього. **Контраст тут ні до чого** —
гард пройшов, це не читабельність, а втрата кольорової ідентичності. Власник
обрав лишити 40% скрізь, тож це СВІДОМЕ рішення, а не недогляд: не «виправляй»
його підняттям альфи, не спитавши.

**A/B-порівняння кадрів — те, чим це знайдено, і воно замінює недоступний
`-diff.png`.** `tests/e2e/_ab-shots.spec.ts` (інструмент, `PERF=1`) знімає всі
25 кроків у вказану теку; `scripts/compare-shots.py` порівнює дві теки й друкує
частку змінених пікселів та МЕЖІ області зміни. Сенс саме в порівнянні ДВОХ
ВЕРСІЙ КОДУ в одному браузері: різниця збірок Chromium (141 тут проти 148 на
CI) входить в обидва знімки однаково і в різниці зникає — тобто з пісочниці
нарешті видно, що зробила зміна. Артефакт CI сюди не завантажується: редирект
на blob-сховище поза allowlist проксі дає 403.
Порядок: зняти «після» → `git worktree` на попередній коміт → зібрати → зняти
«до» → порівняти. **Пастка, вже наступана:** `_`-префіксні спеки вимкнені
`testIgnore`, тож без `PERF=1` прогін мовчки не знаходить жодного тесту. Друга:
інструмент НЕ глушить анімації, тож ілюстрації з нескінченним рухом
(`b3dFloat`, `sparkleFloat` на гостьовому екрані) дають різницю, якої немає —
перевіряй кроп очима, перш ніж вважати це регресією.

**Третій випадок, коли A/B знайшов те, чого не бачить ЖОДЕН гард** (після
зеленої кнопки, що стала бурою, і знятої рамки фокуса): полиск на будинку.
Окремий шар 120×150 з альфою `.30` читався як сіра смуга через увесь герой.
Гардам нема за що зачепитись — геометрія валідна, контраст не зачеплено,
властивості композитні. **І перша спроба виправити не спрацювала**: зменшений
шар із `mix-blend-mode:screen` усе одно лишав слід ліворуч-знизу, бо річ не в
розмірі — окремий прямокутник поверх сцени вилазить за силует ЗА ПОБУДОВОЮ.
Робоче рішення конструктивне: полиск усередину SVG, на самі грані, де його
форма обмежена гранню. Той самий хід, що з радіусами — не підганяти число, а
прибрати можливість помилки.

**Третя пастка A/B, наступана в серпні: інструмент МУСИТЬ морозити час.** Дві
теки знімаються з інтервалом у десятки хвилин, тож будь-який текст, похідний від
годинника, відрізняється сам по собі. Прогін «до» об 11:0x і «після» о 12:0x дав
різницю на ТРЬОХ екранах (`db-list`, `guest-home`, `realtor-dashboard`) в
однаковій зоні заголовка — це `greeting()` перемкнувся з «Доброго ранку» на
«Добрий день» (`hour < 12` в utils). Виглядало як регресія від зміни, якої я не
робив. `clock.setFixedTime` тепер у самому інструменті, зі значенням бейслайнів,
щоб кадри двох інструментів лишались зіставними.

**Калібрування, зняте цим же заходом: A/B бачить БІЛЬШЕ за бейслайн, і це
норма.** Порівняння показало зміни на семи екранах (0.14–3.15% пікселів), а
воркфлоу перезняв РІВНО ТРИ кадри. Причина — `maxDiffPixelRatio: 0.01`: усе,
що нижче 1%, бейслайн пропускає, а `--update-snapshots` (режим `changed`)
переписує лише те, що справді впало. Тобто A/B — прилад чутливіший за гард, і
розходження в його користь не є ознакою, що щось поламалось.

**Пастка публікації, теж наступана: коміт від `github-actions[bot]` НЕ
запускає CI.** Пуші під `GITHUB_TOKEN` навмисно не тригерять воркфлоу, тож
після перезняття кадрів прогін на новому коміті або відсутній, або висить у
`action_required`, і схвалити його токеном інтеграції не можна («Resource not
accessible by integration»). Розблоковує це звичайний пуш ЛЮДИНОЮ поверх —
наступний коміт запускає CI нормально.

задокументована (`window.innerHeight` в `addInitScript` віддає вікно ДО
емуляції). Обидві — у Testing, щоб їх не «знаходили» знову.

**Чого цей раунд НЕ дає, і це треба тримати в голові:** Chromium емулює
геометрію, не WebKit. Верстка на цих ширинах доведена; `backdrop-filter`,
каретка під склом і клавіатура — ні. Єдиний свідок для них лишається той
самий: запис екрана з пристрою через `scripts/analyze-recording.py`.

**Три НОВІ класи багів, яких `Modal.tsx` не мав і не міг мати** — тому що він
монтувався ЗАНОВО щоразу (`{show && <Modal>}`), а `ActionSheet` живе довше за
один цикл відкриття/закриття. Кожен клас — falsification-проведений (зламав →
впало → відкотив → зелено), детальний розбір процесу пошуку — вище в сесійному
блоці; тут лише підсумок причини й фіксу:

1. **`moving` (зняття блюру на час руху) губився на ПОВТОРНОМУ відкритті.**
   `const [moving, setMoving] = useState(open)` ловить лише ПЕРШИЙ показ —
   компонент, що живе довше за один цикл, ніколи більше не проганяє цей вираз.
   Другий і кожен наступний `open:false→true` лишав `moving=false`, тобто шит
   блюрив фон під час власного виїзду вдруге. Фікс: `setMoving(true)` явно в
   ефекті на `[open]`, поруч із `setRendered(true)`/`setClosing(false)`. Гард
   (`modal-sweep.spec.ts` → «шит НЕ блюрить фон, поки їде») ловив це як
   `клас руху не виставився на старті` — падав СИСТЕМНО, не зрідка.

2. **Меню, чий пункт відкриває щось ІНШЕ на тому самому екрані, дублює
   `role="dialog"`.** «Меню бази» → «Папки»/«Виділити обʼєкти»/«Змінити
   порядок»/видалення бази (через `confirmAction`) — усі роблять
   `setShowMenu(false)` і в ТОЙ САМИЙ обробник відкривають щось нове. У старому
   `Modal.tsx` це не мало наслідків: `setShowMenu(false)` унмаунтив шит МИТТЄВО
   (звичайний умовний рендер). У `ActionSheet` те саме `setShowMenu(false)`
   лише СТАРТУЄ вихідну анімацію (~250мс) — і весь цей час старий шит
   співіснує з новою модалкою/режимом. Playwright ловив це як strict-mode
   violation (`.modal` resolved to 2 elements) на `folders-wire.spec.ts` (5
   тестів), `modal-a11y.spec.ts`, `owner-workflow.spec.ts` — але реальна
   причина серйозніша за тести: два одночасні `role="dialog"` плутають фокус і
   Escape для читалки. Фікс — НЕ в `ActionSheet` (він не може знати, що
   викликач збирається показати далі), а в `DatabaseObjectsScreen`: меню-шит
   демонтується ВІДРАЗУ, без анімації, щойно `selectMode`/`reorderMode`/
   `showFolderManage`/`confirmOpen` (підписка на `confirmRequest` у сторі)
   стає true — `{!selectMode && !reorderMode && !showFolderManage && !confirmOpen
   && <ActionSheet …>}`. Навігаційні пункти («Аналітика», «Календар» тощо)
   цього не потребують — вони перемикають ЕКРАН, і шит демонтується разом з
   усім деревом автоматично.

3. **Найглибший: `animationend`/страховка від ПЕРЕРВАНОГО закриття долітають
   ПІСЛЯ реоткриття того самого персистентного шита й розмонтовують його
   заново.** `ConfirmHost` — ОДИН екземпляр на весь застосунок, і сценарій
   «відповів на підтвердження → інше місце одразу питає НОВЕ підтвердження»
   (типово для `ShareSheet`: revoke-confirm → askRevive-confirm ×2 → rotate-
   confirm, усі поспіль) реально трапляється швидше за 240мс `modalSlideDown`.
   Коли реоткриття (`open:false→true`) приходить, поки СТАРА CSS-анімація
   виїзду ще грає на ТОМУ Ж DOM-вузлі (той самий `<div>` перевикористовується,
   бо компонент персистентний), браузер планує зміну на `modalSlideUp` — але
   ПРИРОДНИЙ `animationend` перерваного `modalSlideDown` інколи встигає
   долетіти вже ПІСЛЯ того, як React синхронно закомітив реоткриття. Обробник
   тоді бачить ЦІЛКОМ коректний `animationName:'modalSlideDown'`, тож перша
   спроба фікса — фільтр за іменем анімації — НЕ ДОПОМОГЛА: подія не
   підроблена, вона просто про цикл, який реоткриття вже скасувало. Знайдено
   не здогадом, а логуванням `open`/`closing`/`rendered`/`moving` у кожному
   ефекті й обробнику з таймстемпами (`console.log` в `onAnimationEnd`, зняте
   через `page.on('console', …)`) — лог показав `animationend {closing:true}`
   за 41мс ПІСЛЯ `open-effect {open:true}` для того самого шита.
   **Правильне джерело правди — не `closing`, а `open`:** `openRef` (мутація
   рефа під час рендеру, синхронна, тож завжди випереджає нативну подію з черги
   задач браузера) тепер керує ОБОМА місцями, що можуть розмонтувати шит —
   `onAnimationEnd` І 320мс страховкою на випадок, якщо `animationend` не
   прийде взагалі: якщо `openRef.current` каже «маю бути відкритим», жодна з
   двох НЕ чіпає `rendered`. Тест `share-flow.spec.ts` (ланцюг із чотирьох
   підтверджень поспіль) — найкращий детектор цього класу; фальсифіковано
   `--repeat-each=15` (75 прогонів, 0 падінь) до фіксу консистентно падав
   (спершу 6/6, після проміжного half-фіксу 2/11 — тобто рідкісний, не
   вакуумний).

**Урок ширший за конкретний фікс:** персистентний компонент (мовтується раз,
живе довше за один цикл видимості) — це ІНША категорія багів, ніж
`Modal.tsx`-стиль (монтується заново щоразу). Клавіатурні правила
`Modal.tsx`/«ПОДВІЙНИЙ ЛІФТ» вище стосуються ВИКЛЮЧНО історичного файлу —

## Changelog — експорт: PDF, який ніколи не працював, і Excel, який не відкривався (серпень 2026)

Три запити власника поспіль про експорт, і **найважливіше зʼясувалось першим:
експорту в PDF у проді не існувало ніколи.** `jsPDF` не має кирилиці, тож
`ExportScreen` довантажує Roboto з `public/fonts/` — а теки `public/` у
репозиторії НЕ БУЛО ЖОДНОГО РАЗУ за всю історію (перевірено по всіх комітах).
Ховала це одна властивість платформи: **`fetch` на 404 НЕ КИДАЄ** — він віддає
`ok:false` і тіло сторінки помилки, тобто `await res.arrayBuffer()` успішно
повертав HTML, а помилка ковталась. Кнопка виглядала робочою. Шрифти
завендорені (~515 КБ × 2, перевірено 2770 кодпойнтів), а `fetch` тепер голосний
(`if (!res.ok) throw`).

**Excel відкривався сирим ZIP-ом** (скріншот власника). Причина не в файлі:
**webview Telegram ігнорує `<a download>`** і НАВІГУЄ на blob-URL, тобто показує
байти замість того, щоб віддати файл. Робочий шлях — Web Share API
(`navigator.share({ files })`), спільний тепер для обох форматів; `<a download>`
лишився фолбеком для звичайного браузера.

**Грошова помилка в самому файлі, знайдена при звірці з екраном.** У вибірці
експорту не було `area_basis`, а `basisArea()` без нього падає на розрахункову
площу — тож обʼєкт із базою «корисна» друкував **$2 160 замість $1 800 на
екрані**. Той самий запит сортувався за назвою, а не за `sort_order`, тобто
порядок у документі не збігався з порядком у застосунку.

### Вміст: половини картки в документі не було

Власник назвав орендаря — виявилось, бракувало сімох полів: **орендар, дати
договору, ціна продажу, адреса, база розрахунку, експлуатаційні послуги,
фото**. Найгірший випадок — обʼєкт НА ПРОДАЖ: він діставав секцію «Оренда» з
чотирьох «—», великий блок «Разом на місяць: —», а ціни не показував ніде.
Тепер секції умовні (`hasRent`, `ОРЕНДАР`, `ПРОДАЖ`), а порожній рядок пари не
малюється взагалі — підпис, який стверджує, що дані мали б бути, гірший за
відсутність підпису.

Формат — світлий за замовчуванням (**Класик**/**Модерн**) плюс **Нічний** як
опція (рішення власника); фото — до 4 (велике + смужка на три), теж рішення
власника.

### Що знайшлось ЛИШЕ тому, що рендер дивились очима

Ключове: PDF не можна перевірити асертом — текст у ньому це гліфи субсету
шрифту. Тому зроблено `_pdf-preview.spec.ts` (інструмент, `_`-префіксний):
генерує документ, перехоплює його стабом `navigator.share`, і рендерить
сторінки в PNG через pdf.js у Chromium (`pdftoppm` у пісочниці немає). Кожен
прохід очима знаходив дефекти, яких не бачив жоден із 300 тестів:

- **Заголовок обкладинки — 1.63:1.** Назва бази малювалась `TXPRI` (#111827,
  колір тексту СТОРІНКИ) на кольоровій смузі #1E3A8A. На зменшеному прев'ю це
  виглядало білим, і я мало не пропустив — довів **пробою пікселів**, а не
  оком. Стало 10.24:1. Правило: на смузі колір може бути лише `onAccent`.
- **Емодзі друкуються порожнечею.** «📍» і «✓» гліфів у вбудованому Roboto не
  мають, тож рядок адреси починався з видимого відступу, а «Так ✓» був просто
  «Так» із дірою. У документ з субсетом шрифту емодзі не кладуть.
- **`clip()` у jsPDF мовчки не працює.** Перша версія фото обрізала їх
  `roundedRect(...,null) + clip()` — знімки вилазили за рамку й накривали
  півсторінки. Лікується попереднім кропом на canvas до фіксованої пропорції
  (побічний виграш: файл 4938 КБ → 258 КБ).
- **Смужка фото зникала мовчки.** Жорсткі висоти означали, що на щільній
  сторінці вона не влазила на кілька міліметрів і не малювалась узагалі —
  обʼєкт із трьома фото показував одне, і причину не було видно ніде. Тепер
  блок МАСШТАБУЄТЬСЯ під залишок сторінки (спільний множник зберігає пропорцію
  кропу) і центрується — притиснутий до лівого поля зменшений блок читався не
  як менше фото, а як зʼїхала верстка.
- **Ритм 3мм між парами полів** ставив підпис наступного поля впритул під
  значення попереднього («100 м² / ПОВЕРХ» читалось одним блоком).
- **Гроші форматувались двома способами в одному файлі** — плитка обкладинки
  «$26 800» проти «$25000» у таблиці й на сторінці обʼєкта.
- **Ставка повторювала власний підпис**: «25000 $ / міс (фіксована)» під
  заголовком «СТАВКА ОРЕНДИ», ще й із пробілами навколо скісних, що рвали
  число й одиницю на три слова. Один форматер (`rateOf`) на весь документ.

### Гард на шрифт — джерельний, і це принципово

## Changelog — аудит доступів: гості, шаринг, команда (серпень 2026)

Запит власника: перевірити керування гостями, функції «поділитися» і команду
бази, знайти що покращити. Найважливіше знайшлось не в UI, а в тому, що ці
екрани **рапортували успіх безпекової дії, якої не сталось**.

### КРИТИЧНО: відкликання доступу не доводило запис

`handleRevoke` у `ManageGuestsScreen` і `TeamScreen` робив
`.update({status:'revoked'}).eq('id', id)` **без** `.select('id')` +
`assertAffected` — тобто був єдиним місцем застосунку, яке лишилось поза
правилом 8 Security rules, і водночас єдиним, де ціна помилки — БЕЗПЕКА, а не
дані. Під RLS заблокований UPDATE повертає порожній набір і NULL у `error`,
тож екран малював бейдж «Відкликано», а доступ лишався ЖИВИМ. Власник дізнався
б про це, лише побачивши чужі правки у своїй базі.

**Чому клас пережив попередній раунд `assertAffected`.** Той раунд ішов по
ХУКАХ (`useProperties`, `useDatabases`, `useFolders`) — а ці дві мутації живуть
прямо в екранах. Урок для наступного разу: греп по `.update(`/`.delete(` мусить
покривати `src/screens`, не лише `src/hooks`.

**Чому наявний тест цього не бачив.** `team.spec.ts` мокав PATCH як «успіх із
рядком» — тобто моделював успіх там, де реальний бекенд моделює НЕОДНОЗНАЧНІСТЬ.
Це те саме, про що вже сказано в changelog аудиту дій з базою: мок, який не
вміє відмовити мовчки, робить зелений тест доказом нічого.

### «Збою не сталось, просто нічого немає» — той самий клас ТРИЧІ

`catch` показував тост і лишав список порожнім, тож збій мережі малював
«Немає запрошень» / «Команди поки немає» / «Немає переглядів». Тост зникає за
секунди, порожній стан лишається на екрані — і читається як ВПЕВНЕНА відповідь
про дані, яких екран ніколи не бачив. Для питання «які доступи я роздав» це
найгірша з можливих неправд. Усі три екрани отримали `loadErr` + `RetryState`
(в аналітиці — через `reloadKey`, бо завантаження живе в `useEffect`).

### Мертвий лінк можна було надіслати

`buildDeepLink` віддає `#`, коли не задано юзернейм бота. `CreateInviteScreen`
цей випадок уже ловив (`usable`), а СПИСКИ гостей і команди — ні: кнопка
«Поділитись» спокійно відправляла сміття, і власник дізнавався б про поломку
від одержувача. Той самий клас уже давав прод-інцидент із `TELEGRAM_APP_NAME`.

### Дизайн-система в рядках доступу

Кнопки рядка були інлайновими стилями з `padding:'6px 0'` — **~26px** проти
44px HIG, і неактивність показувалась через `opacity:.6`, що прямо суперечить
правилу «неактивність показує КОЛІР» (над темним склом прозорість зʼїдає
елемент). Заведено спільний `.acc-act` (share/revoke/disabled). Це НЕ
`.obj-act-btn`: там 35px — свідомий виняток, бо над кнопками лежить тіло
картки, яке відкриває обʼєкт; тут картка не клікабельна, тож повні 44px
беруться безкоштовно. Додано «Копіювати» — доти лінк можна було лише
відправити в Telegram.

**Гіпотезу про переповнення СПРОСТОВАНО заміром:** три кнопки в рядку на 360px
виглядали як гарантований оверфлоу (розрахунок давав ~101px підпису на ~83px
кнопки), але `devices.spec.ts` + `screen-text-fit.spec.ts` пройшли на всіх
пʼятьох ширинах. Рахунок «на серветці» не врахував, що іконка й падінги
стискаються — міряти, а не прикидати.

### Нові гарди

`guests-manage.spec.ts` — керування гостями не мало ЖОДНОГО функціонального
тесту: екран відвідували лише візуальні обходи, тобто перевірялось, як він
ВИГЛЯДАЄ, і ніколи, що він РОБИТЬ. Чотири кейси: відкликання доходить до
сервера; заблокований RLS не малює «Відкликано»; збій завантаження дає повтор,
а не «Немає запрошень»; мертвий лінк вимикає обидві дії. Плюс дзеркальний гард
RLS у `team.spec.ts` — фіксити один із двох екранів-копій без гарда на другий
означало б, що наступна правка знову їх розведе.

**Пастка власного заміру, наступана тут же:** перша версія гарда читала
прапорець `patched` СИНХРОННО після кліку по підтвердженню — і падала на
власному замірі, а не на коді. Підтвердження й запит асинхронні, тож потрібен
`expect.poll`.

Усі гарди falsification-проведені: прибрав `assertAffected` → впав гард RLS;
прибрав `RetryState` → впав гард порожнечі; повернув → зелено.

### Знайдено, НЕ виправлено (потребує міграції або рішення власника)

- **Власник не бачить, ХТО прийняв гостьовий лінк.** `db_members` має
  `member_name` (його заповнює `claim_team_invite`), а `guest_links` —
  тільки `guest_user_id` без імені. Тобто в команді видно реальне імʼя, а в
  гостях — лише власний підпис («Орендар 5»). Симетрія вимагає міграції
  (колонка + запис у `claim_guest_link`) плюс толерантного select-а на
  клієнті (ретрай на `42703`, як `folder_id` у `useProperties`) — інакше
  екран ляже до застосування. З цього середовища міграції не застосувати, а
  045/046 ще чекають, тож новий гейт на міграцію свідомо не заводився.
- **Відкликані рядки накопичуються назавжди** — видалення немає, список
  росте. Потрібне рішення: ховати за фільтром чи давати видаляти.
- **Два екрани-копії.** `ManageGuestsScreen` і `TeamScreen` — дзеркала, і саме
  тому кожен дефект цього раунду був подвійним. Це вже ТРЕТІЙ випадок
  (перший породив `InviteSheet`). За правилом «рецепт утретє — це токен» тут
  напрошується спільний `AccessListScreen` із `kind`, як уже зроблено для
  `CreateInviteScreen`.

## Changelog — доступи: один екран замість двох копій, імена, згорнуті відкликані (серпень 2026)

Продовження аудиту доступів. Попередній раунд полагодив дефекти, цей прибирає
причину, через яку кожен із них існував ДВІЧІ, і закриває три пункти, що

### `AccessList` — один компонент на гостей і команду

`ManageGuestsScreen` і `TeamScreen` були дзеркальними копіями: **кожен** дефект

Тепер логіка й розмітка живуть у `src/components/AccessList.tsx` із

Інлайнові стилі рядка переїхали в класи (`.acc-card`/`.acc-av`/`.acc-name`/
`.acc-badge`/`.acc-meta`/`.acc-note`) — інакше «спільний компонент» лишався б
спільним лише наполовину.

### Імʼя того, хто прийняв (міграція 048)

Деталі — у Pending manual actions §0k. Головне для клієнта: `select` іде з

Підпис власника лишається ПОРЯД з іменем, а не замість нього: «Орендар, кв. 5»
каже, за що доступ, а імʼя — кому.

### Відкликані згорнуті — і чому це потягнуло за собою тост

Видалення рядків немає, тож за рік активного користування база накопичує
десятки мертвих доступів, і живі опиняються за фолдом рівно тоді, коли їх
найбільше. Відкликані тепер у згорнутій секції з лічильником.

**Наслідок, який видно лише після зміни:** відкликаний рядок ЇДЕ туди одразу,
тобто зникає з очей — а доти фідбеком дії був сам бейдж «Відкликано» на місці.
Без тоста дія завершувалась мовчазним зникненням рядка, що читається як збій,
а не як успіх. Тому `handleRevoke` тепер показує тост; це не косметика, а
заміна фідбеку, який забрала сама фільтрація.

Окремий випадок — коли відкликані ВСІ: активна секція порожня, але список не
порожній, тож замість «Немає запрошень» (неправда) малюється «Активних
доступів немає».

### Пастка фальсифікації, наступана тут же

Перша спроба зламати ретрай `42703` не дала падіння — і це виглядало як
вакуумний гард. Насправді правка лишила `let`, яке більше ніде не
перевизначається, збірка впала на лінті, а `npm run build >/dev/null 2>&1`

## Changelog — бейслайни тихо стухали: `--update-snapshots` ≠ «перезняти все» (серпень 2026)

Знайдено під час аудиту доступів, і це дефект самої ІНФРАСТРУКТУРИ бейслайнів,
а не застосунку.

**Воркфлоу декларував одне, а робив інше.** У шапці `update-snapshots.yml`
стояло «перезнімає кадри беззастережно», а команда була
`npx playwright test screenshots --update-snapshots`. У Playwright 1.60 голий
прапорець має **пресет `changed`** (`preset: "changed"` у `--help`), тобто
перезнімає ЛИШЕ ті кадри, що НЕ ПРОЙШЛИ порівняння. Кадр, чий діф не дотягнув
до `maxDiffPixelRatio: 0.01`, не оновлювався НІКОЛИ.

**Як спіймалось.** Рядок доступів змінив верстку (три текстові кнопки → дві
іконкові + одна текстова), я запустив воркфлоу — і він відзвітував «бейслайни
вже збігаються, комітити нічого», хоч кадр показував СТАРУ верстку. Гліфів
змінилось менше за поріг: фон кнопок — напівпрозоре скло, різниця по пікселю
нижча за `threshold`, тож рахувались лише чорнила підписів.

**Масштаб виявився більшим за привід.** Після `=all` перезнялось **29 кадрів**,
а не два — тобто дрейф нижче порога накопичувався давно й тихо по всьому
набору. Чотири кадри (`/v`-сторінки, `share-sheet`) впали в розмірі на 25–30%,
що виглядало як втрата вмісту; **очна звірка старого й нового показала
ідентичну картинку** — це перекодування PNG, не регресія. Перевіряти це було
обовʼязково: воркфлоу сам попереджає, що так само радо благословить справжню
регресію.

**Наслідок, який робить дефект вартим окремого запису:** він НЕВИДИМИЙ. Гард не
падав, воркфлоу звітував успіх, а еталон розходився з рендером — тобто
наступна СПРАВЖНЯ регресія в тій зоні порівнювалась би зі стухлим кадром і
пройшла б. Правильний прапорець — `--update-snapshots=all`.

**Ширший урок сесії.** Це третій випадок поспіль, коли зелений результат
означав не «все добре», а «цього не перевіряли»: (1) мок відкликання віддавав
успіх БЕЗ рядків — форму, яка на реальному бекенді означає відмову RLS;
(2) `.acc-act` не було в переліку селекторів перевірки вильоту підпису, тож
дефект на 22–31px не бачив ніхто; (3) бейслайн не перезнімався, бо діф не
дотягував до порога. Спільне в усіх трьох — **зелений тест не відрізняється від
відсутнього тесту, доки не спитати, що саме він міряє.**
