```sql
-- Політики сповіщень: мусить бути ТРИ окремі (035), а не одна notifs_own
SELECT policyname FROM pg_policies WHERE tablename='notifications' ORDER BY 1;

-- Колонки, без яких падає список обʼєктів

 ('manage_share','subscribe_to_shared_db','claim_team_invite','claim_guest_link',
  'delete_my_account','record_public_view','get_public_db_preview','is_guest_of_property')
 ORDER BY 1;

SELECT tablename FROM pg_publication_tables WHERE pubname='supabase_realtime';

-- Чи закрита RLS-діра гостьових лінків (046)
SELECT with_check IS NOT NULL AS has_with_check
  FROM pg_policies WHERE tablename='guest_links' AND policyname='glinks_owner_all';

-- ── КОМАНДА: чи вона взагалі існує в цій базі ──
SELECT to_regclass('public.db_members') AS db_members;
SELECT proname FROM pg_proc WHERE proname IN
 ('get_editor_db_ids','get_editor_property_ids','get_editor_db_ids_from_auth_uid',
  'claim_team_invite') ORDER BY 1;
-- Очікуємо editor-політики на properties/photos/pfiles/rent_*/storage/folders/views
SELECT tablename, policyname FROM pg_policies

-- Чи застосована 045: ОБИДВІ функції мусять мати домен-якір і tg_id > 0.

SELECT proname,
       prosrc LIKE '%telegram.propspace.app%' AS has_domain_anchor,
       prosrc LIKE '%tg_id > 0%'              AS has_nonzero_guard
  FROM pg_proc WHERE proname IN
 ('get_app_user_id_from_auth_uid','get_editor_db_ids_from_auth_uid') ORDER BY 1;
```

## 3. Накотити відсутні міграції

### Найпростіший шлях: ОДИН файл

`supabase/RELEASE.sql` — усі невикочені міграції (048–061) в одному файлі.
Вставити в Dashboard → SQL Editor і виконати. Далі — `verify_release.sql`,
де всі рядки мають бути `✅ OK`.

Три властивості файлу ДОВЕДЕНІ виконанням у CI, а не заявлені:

| властивість | як доведено |
|---|---|
| дає ТУ САМУ схему, що поштучний накат | звірка 438 обʼєктів (функції з хешем визначення, політики з хешем предикатів, колонки, обмеження, ACL) |
| ідемпотентний | другий накат поспіль → схема не змінилась |
| атомарний | обгорнутий `BEGIN/COMMIT`; підставлена помилка → відкат, `public_phone` не зʼявився |

Файл **згенерований** (`scripts/build-release-sql.sh`), а не написаний руками:
джерело правди лишається в `supabase/migrations/`, і CI падає, якщо вони
розійшлись. Правити треба міграцію, потім перезібрати.

**Порядок усередині файлу вже правильний.** Таблиця нижче лишається для
випадку, коли міграції накочують поштучно.

**Чому 051 не можна відкладати.** Обидва клієнтські порядки зламані, і це
перевірено, а не припущено: файли до RPC — при збої користувач лишається в
акаунті без жодного фото; файли після RPC — політика storage не матчить нічого
(`properties` знесені каскадом, `auth.users` теж), тобто DELETE стирає нуль
обʼєктів і рапортує успіх. Тому клієнт тепер не чіпає storage взагалі, і
єдиний, хто це робить, — функція з 051.

051 несе власний доказ: рахує, скільки обʼєктів лежить у бакеті, звіряє з
`ROW_COUNT` і повертає `storage_not_cleared` замість `deleted = true`, якщо не
збіглось. Акаунт при цьому НЕ видаляється — стан «є акаунт і є файли»
оборотний, «немає акаунта, є файли» ні.

**Про порядок 052 і 053 — чесно, бо попереднє формулювання було
нездійсненним.** Тут стояло «053 не пізніше за 052, порядок жорсткий». За
номерами файлів це неможливо: і `supabase db push`, і
`scripts/verify-migrations.sh` беруть їх відсортованими, тобто 052 ЗАВЖДИ
раніше. Документ вимагав того, чого жоден інструмент репозиторію не робить.

Що правда: підкинутий на чужий обʼєкт розклад змушує крон надсилати
АТАКУВАЛЬНИКУ назву обʼєкта жертви та імʼя її орендаря, і доти це не
працювало лише тому, що нагадування були зламані типом результату.

Чому це НЕ вимагає зворотного порядку: вікно існує лише між двома міграціями
одного накату (секунди), його експлуатація потребує рядка, ПІДКИНУТОГО
РАНІШЕ, а ремонтний блок 053 такі рядки переприсвоює власнику цілі. Плюс сама
053 додає `rp.owner_id = p.owner_id` у функцію нагадувань, тобто навіть
уцілілий підкидень у розсилку не потрапляє.

Практична вимога тому одна: **накочувати 052 і 053 РАЗОМ, одним заходом.**
Лишити застосованою 052 без 053 — не можна.

Тобто галочка «воркфлоу запущено» нижче нічого не означає без 052: відповідь

### 6.5. Команда — розгорнуто

Автогарди (`team-writes.spec.ts`) доводять, що КЛІЄНТ шле правильні дані й чесно
показує відмову. Саму політику доводить **тільки** цей прогін: у тестах RLS не
бере участі взагалі.

**Передумова.** Спершу зліпок (розділ 0): без `041` команди не існує, без `043`
редактор не створить папку, без `045` його права на фото резолвляться
регресованою ідентичністю, без `047` він бачить «0 переглядів» там, де у
власника цифри.

**Відкриття**
- [ ] Власник створює інвайт → другий акаунт відкриває `team_`-лінк → у базі
- [ ] База в списку другого акаунта з бейджем «Команда»
- [ ] Другий акаунт із роллю **realtor** бачить її і на домашньому екрані
      (саме та комбінація, на якій редактор колись губив доступ назавжди)
- [ ] Клейнутий учасник зʼявився у власника в «Команді» **з імʼям**

**Збереження в обидва боки** — головне, заради чого все це
- [ ] Редактор **створює обʼєкт** → власник бачить його після оновлення.
      Це найтонше місце: `owner_id` рядка мусить бути ВЛАСНИКА, інакше
      `WITH CHECK` у 041 відмовить і обʼєкт «просто не збережеться»
- [ ] Редактор створює **кілька обʼєктів пакетом** (окремий шлях у коді)
- [ ] Власник змінює статус → **редактор бачить зміну**
- [ ] Редактор завантажує **фото** → власник його бачить
      (шлях через `045` + edge `validate-upload` — ламається найтихіше)
- [ ] Редактор **підтверджує платіж** → власник бачить у календарі
- [ ] Редактор створює **папку** і переносить у неї обʼєкт

**Відображення**
- [ ] Статистика бази в редактора збігається з власницькою
- [ ] Валюта — **власника бази**, не редактора
- [ ] Лічильник переглядів у редактора не нульовий (потребує `047`)

**Доступ не падає**
- [ ] Редактор працює 10+ хвилин, перемикає екрани — доступ живий
- [ ] Холодний старт редактора (вбити застосунок) → база на місці
- [ ] Власник відкликає, поки редактор **усередині бази** → наступне збереження
      дає зрозуміле повідомлення, а не тиху «успішну» зміну
- [ ] Редактор **не бачить** шаринг / гостей / команду / редагування й
      видалення бази

### 6.6. Гість

## Що НЕ перевірено машиною — і чому

Це не перелік підозр, а межа доказовості. Усе нижче зелений CI **не** покриває
за побудовою.

| що | чому машина не бачить | як перевірити |
|---|---|---|
| ~~Міграції~~ | **тепер ВИКОНУЮТЬСЯ**: `scripts/verify-migrations.sh` піднімає одноразовий Postgres, накочує всі міграції й ганяє поведінкові перевірки (робота `migrations` у CI). Лишається неперевіреним лише те, що залежить від СТАНУ живої БД — які міграції на ній насправді застосовані | `supabase/verify_release.sql` у Dashboard: усі рядки мають бути `✅ OK` |
| ~~Реальний RLS~~ | **тепер ВИКОНУЄТЬСЯ**: `scripts/verify-rls.sql` входить у ролі через email-клейм JWT і перевіряє власника проти чужого, гостя, редактора, anon і storage. Чого він НЕ покриває: поведінку самого PostgREST і storage-API (який саме набір клеймів вони ставлять) | розділ 6, з ДВОМА акаунтами — він лишається обовʼязковим саме через цей шар |
| **Edge-функції** | Deno в пісочниці немає; `edge-invariants` перевіряє ДЖЕРЕЛО на відомі граблі, а не поведінку | розділ 5 + логи Supabase |
| **Поведінка WebKit** | Playwright тут — Chromium; `backdrop-filter`, каретка під склом і клавіатура в WebKit недосяжні | запис екрана з iPhone → `scripts/analyze-recording.py` |
| **Прозорість/контраст на пристрої** | гарди міряють рендер Chromium | очима, на живому телефоні |

**Окремо про 051.** Щаслива гілка доказу виконується в CI на кожному прогоні
(`verify-behaviour.sql`), і гілка «власник не бачить storage» — теж. Чого CI
НЕ покриває: справжній S3. `DELETE FROM storage.objects` прибирає рядки
метаданих — саме вони роблять файл досяжним через Storage API і публічний
URL; чи звільняє Supabase блоб фізично, звідси не перевірити.

Тому перед тим, як покладатись на неї, зроби тестове видалення на ПОРОЖНЬОМУ
акаунті: очікуваний результат `deleted = true`, і прямий URL раніше видимого
фото має віддавати 404.

## Що робити, якщо щось пішло не так

- **«Помилка завантаження» у списку обʼєктів** → не застосована `042`.
- **«Поділитися базою» не працює** → немає `036`/`037`.
- **Розділ «Команда» не створює інвайт** → немає `041`.
- **Немає розділу «Папки»** → немає `043`; це не поломка, фіча просто вимкнена.
- **Бот мовчить на `/start`** → не заданий `TELEGRAM_WEBHOOK_SECRET`.
- **Шери відкривають порожній чат бота** → `TELEGRAM_APP_NAME` заданий як URL
  замість short name.
- **Сповіщення не приходять** → не додано `SUPABASE_SERVICE_ROLE_KEY` або не
  запущено `send-reminders.yml`.
- **Раптом зникли всі права / все віддає «немає доступу»** → хтось запустив
  `013`/`016` повторно. Накотити 017–046 заново.
