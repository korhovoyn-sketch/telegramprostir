Тут лише те, **чого автотести перевірити не можуть**: справжній Supabase із
живим RLS, справжній Telegram, справжні edge-функції і другий акаунт. Уся
тестова база герметична (`page.route`-моки), тож зелений CI **не** є доказом,
що бекенд налаштований.

Порядок має значення. Не перестрибуй розділи.

## 0. Перед усім — зняти зліпок стану

Supabase → SQL Editor. Спершу `supabase/verify_release.sql`, потім:

```sql
-- Політики сповіщень: мусить бути ТРИ окремі (035), а не одна notifs_own
SELECT policyname FROM pg_policies WHERE tablename='notifications' ORDER BY 1;

-- Колонки, без яких падає список обʼєктів
SELECT column_name FROM information_schema.columns
 WHERE table_name='properties' AND column_name IN ('area_basis','folder_id','parking_type','ev_charger');

-- RPC, які викликає клієнт
SELECT proname FROM pg_proc WHERE proname IN
 ('manage_share','subscribe_to_shared_db','claim_team_invite','claim_guest_link',
  'delete_my_account','record_public_view','get_public_db_preview','is_guest_of_property')
 ORDER BY 1;

-- Realtime для сповіщень (034)
SELECT tablename FROM pg_publication_tables WHERE pubname='supabase_realtime';

-- Чи закрита RLS-діра гостьових лінків (046)
SELECT with_check IS NOT NULL AS has_with_check
  FROM pg_policies WHERE tablename='guest_links' AND policyname='glinks_owner_all';

-- ── КОМАНДА: чи вона взагалі існує в цій базі ──
SELECT to_regclass('public.db_members') AS db_members;
SELECT proname FROM pg_proc WHERE proname IN
 ('get_editor_db_ids','get_editor_property_ids','get_editor_db_ids_from_auth_uid',
  'claim_team_invite') ORDER BY 1;
-- Очікуємо editor-політики на properties/photos/pfiles/rent_*/storage/folders/views
SELECT tablename, policyname FROM pg_policies
 WHERE policyname LIKE '%editor%' ORDER BY 1,2;
-- Чи застосована 045: ОБИДВІ функції мусять мати домен-якір і tg_id > 0.
-- Без цього права редактора на фото резолвляться неправильною ідентичністю.
SELECT proname,
       prosrc LIKE '%telegram.propspace.app%' AS has_domain_anchor,
       prosrc LIKE '%tg_id > 0%'              AS has_nonzero_guard
  FROM pg_proc WHERE proname IN
 ('get_app_user_id_from_auth_uid','get_editor_db_ids_from_auth_uid') ORDER BY 1;
```

## 2. Полагодити конвеєр міграцій

**Факт:** `migrate.yml` має 15 запусків і **всі впали** з
`SUPABASE_DB_PASSWORD secret is not set`. Тобто **жодної міграції CI не накотив
ніколи** — усе, що є в базі, потрапило туди руками.

1. Settings → Secrets and variables → Actions → додати `SUPABASE_DB_PASSWORD`.
2. Запустити `migrate.yml` **вручну** (`Run workflow`) з **`baseline=true`**.
   Це позначить наявні міграції як застосовані, **не виконуючи** їхній SQL.
   Без цього кроку перший автоматичний прогін спробує накотити `001` поверх
   живої бази.
3. Переконатись, що прогін зелений.

- [ ] Секрет додано
- [ ] Baseline виконано (`baseline=true`), прогін зелений
- [ ] Наступний push у `main` накотив міграції без помилок

## 3. Накотити відсутні міграції — ПОРЯДОК ОБОВʼЯЗКОВИЙ

Залежності реальні, не стилістичні:

| Черга | Міграція | Чому саме тут |
|---|---|---|
| 1 | `045` | **Першою**, якщо 038 або 041 уже застосовані: лікує регресію ідентичності, яку внесла 038 і розтиражувала 041 |
| 2 | `036` + `037` | Без них немає `manage_share` і `subscribe_to_shared_db` — шаринг баз не працює взагалі. 037 самодостатня |
| 3 | `038` | Закриває запис у чужі фото. Потребує задеплоєної `validate-upload` |
| 4 | `039` | Паркінг-поля + `per_day` |
| 5 | `040` | **Саме після 039**: перевизначає `get_public_property_preview` разом із паркінг-полями. Зворотний порядок їх зітре |
| 6 | `041` | Команда. **Після 038** |
| 7 | `042` | **Критично: до деплою фронта.** `area_basis` у головному SELECT **без** фолбеку → список обʼєктів дає «Помилка завантаження» |
| 8 | `043` | Папки. Після 041 |
| 9 | `044` | Видалення акаунта |
| 10 | `046` | RLS-діра гостьових лінків: підроблений лінк давав читання чужої бази |
| 11 | `047` | Редактор команди бачить лічильник переглядів. Без неї RLS віддає порожньо БЕЗ помилки, тож редактор бачить «0» там, де у власника цифри |

### ⛔ НІКОЛИ не запускати повторно `013_master_setup.sql` і `016_complete_setup.sql`

Обидві містять цикл, що робить `DROP POLICY` для **всіх** політик схеми
`public`, а відтворюють лише свій набір. Повторний запуск **стирає політики
всіх міграцій 017–047**: лок інсертів сповіщень (035), RLS файлів (033), права
команди (041), гостьовий фікс (046).

- [ ] Усі відсутні міграції накочені в цьому порядку
- [ ] `verify_release.sql` повторно — усе зелене

## 6. Наскрізний прогін по ролях (два акаунти!)

Потрібні **два різні Telegram-акаунти**. Найважливіші пункти — ті, де RLS
вирішує доступ, бо в тестах RLS не бере участі взагалі.

### 6.1. Реєстрація
- [ ] Новий акаунт → вхід → вибір ролі → профіль → домашній екран
- [ ] У `users` зʼявився рядок із правильною роллю
- [ ] Кнопка «Назад» Telegram на кроках онбордингу не веде в нікуди

### 6.2. Вхід і вихід
- [ ] Вихід → повторний вхід тим самим акаунтом
- [ ] Холодний старт після примусового закриття застосунку
- [ ] Вхід із другого пристрою тим самим акаунтом

### 6.3. База
- [ ] Створити базу → додати обʼєкти → фото → експорт PDF і Excel
- [ ] Видалити базу і переконатись, що вона зникла (а не «зникла» лише в UI)

### 6.4. Шаринг — **найважливіше**
- [ ] Власник ділиться базою
- [ ] **Другий акаунт** відкриває лінк → підписується → бачить дані
- [ ] Власник тисне «Оновити посилання»
- [ ] **Другий акаунт по старому лінку доступу НЕ має**
- [ ] Власник «Відкликати доступ» → підписаний рієлтор втратив базу
- [ ] Старий лінк на публічній `/v` — мертвий

### 6.5. Команда — розгорнуто

Автогарди (`team-writes.spec.ts`) доводять, що КЛІЄНТ шле правильні дані й чесно
показує відмову. Саму політику доводить **тільки** цей прогін: у тестах RLS не
бере участі взагалі.

**Передумова.** Спершу зліпок (розділ 0): без `041` команди не існує, без `043`
редактор не створить папку, без `045` його права на фото резолвляться
регресованою ідентичністю, без `047` він бачить «0 переглядів» там, де у
власника цифри.

**Відкриття**
- [ ] Власник створює інвайт → другий акаунт відкриває `team_`-лінк → у базі
- [ ] База в списку другого акаунта з бейджем «Команда»
- [ ] Другий акаунт із роллю **realtor** бачить її і на домашньому екрані
      (саме та комбінація, на якій редактор колись губив доступ назавжди)
- [ ] Клейнутий учасник зʼявився у власника в «Команді» **з імʼям**

**Збереження в обидва боки** — головне, заради чого все це
- [ ] Редактор **створює обʼєкт** → власник бачить його після оновлення.
      Це найтонше місце: `owner_id` рядка мусить бути ВЛАСНИКА, інакше
      `WITH CHECK` у 041 відмовить і обʼєкт «просто не збережеться»
- [ ] Редактор створює **кілька обʼєктів пакетом** (окремий шлях у коді)
- [ ] Власник змінює статус → **редактор бачить зміну**
- [ ] Редактор завантажує **фото** → власник його бачить
      (шлях через `045` + edge `validate-upload` — ламається найтихіше)
- [ ] Редактор **підтверджує платіж** → власник бачить у календарі
- [ ] Редактор створює **папку** і переносить у неї обʼєкт

**Відображення**
- [ ] Статистика бази в редактора збігається з власницькою
- [ ] Валюта — **власника бази**, не редактора
- [ ] Лічильник переглядів у редактора не нульовий (потребує `047`)

**Доступ не падає**
- [ ] Редактор працює 10+ хвилин, перемикає екрани — доступ живий
- [ ] Холодний старт редактора (вбити застосунок) → база на місці
- [ ] Власник відкликає, поки редактор **усередині бази** → наступне збереження
      дає зрозуміле повідомлення, а не тиху «успішну» зміну
- [ ] Редактор **не бачить** шаринг / гостей / команду / редагування й
      видалення бази

### 6.6. Гість
- [ ] Гостьовий лінк → клейм другим акаунтом → доступ **лише на читання**
- [ ] Гість не може редагувати
- [ ] Відкликання гостьового лінка забирає доступ

### 6.7. Публічна `/v`
- [ ] Лінки бази / обʼєкта / підбірки відкриваються **з пристрою без Telegram**
- [ ] Ціни у валюті власника (не завжди `$`)
- [ ] Лічильник переглядів росте

## Що робити, якщо щось пішло не так

- **«Помилка завантаження» у списку обʼєктів** → не застосована `042`.
- **«Поділитися базою» не працює** → немає `036`/`037`.
- **Розділ «Команда» не створює інвайт** → немає `041`.
- **Немає розділу «Папки»** → немає `043`; це не поломка, фіча просто вимкнена.
- **Бот мовчить на `/start`** → не заданий `TELEGRAM_WEBHOOK_SECRET`.
- **Шери відкривають порожній чат бота** → `TELEGRAM_APP_NAME` заданий як URL
  замість short name.
- **Сповіщення не приходять** → не додано `SUPABASE_SERVICE_ROLE_KEY` або не
  запущено `send-reminders.yml`.
- **Раптом зникли всі права / все віддає «немає доступу»** → хтось запустив
  `013`/`016` повторно. Накотити 017–046 заново.
