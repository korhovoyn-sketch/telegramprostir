# prostir · маркетингові матеріали

Тека самодостатня: відкрийте **`index.html`** у браузері — це вся презентація
(стратегія, візуальна система, макети, відео). Зовнішніх залежностей немає,
шрифти вендорені, тож рендер однаковий будь-де й без мережі.

Для пересилання одним файлом є `../prostir-marketing.html` — те саме, але з
усім вшитим у data-URI (`node marketing/bundle.mjs`).

```
marketing/
├── index.html          ← ПРЕЗЕНТАЦІЯ. Почніть звідси
├── reel.html           15-секундний рілз як анімована сторінка
├── shots/              16 кадрів продукту, знятих із живого застосунку в 3×
├── creatives/          готові до публікації PNG + відео
├── fonts/              Geologica + JetBrains Mono (обидві змінні, OFL)
├── export.mjs          index.html → PNG-креативи
├── render-reel.mjs     reel.html → WebM (покадрово, два бітрейти)
├── render-board.mjs    reel.html → 5 кадрів сторіборду
├── bundle.mjs          усе разом → один самодостатній HTML
├── verify-bundle.mjs   перевірка ВИХОДУ: чи все намалювалось
└── check-layout.mjs    переповнення по горизонталі на пʼятьох ширинах
```

## Візуальна мова

**Папір навколо скла.** Застосунок — темне скло й градієнти; якщо реклама теж
градієнт, продукт у ній зникає (скляний екран на скляному тлі не має за що
зачепити око — саме цим і хибувала попередня редакція). Тому носій паперовий:
теплий ґрунт `#EFEDE6`, інженерний гротеск **Geologica**, моно-шар даних
**JetBrains Mono**, видима сітка, плівкове зерно, нульовий радіус. Продукт
з'являється на чорнильних розворотах, де світиться.

Постійні елементи кадру — те, що робить із дев'яти плиток одну систему:
моно-шапка (рубрика ліворуч, індекс праворуч), товста лінійка під нею,
реєстраційні мітки в кутах, зерно, знак. Вони є на КОЖНОМУ форматі.

| роль | гарнітура |
|---|---|
| заголовки, текст | Geologica 350 / 700 / 800, трекінг −4,5% на дисплеї |
| дані, мітки, цифри | JetBrains Mono 500 / 700 |

Гротеск говорить, моно **свідчить**: усе, що є вимірюваним фактом — площа,
ставка, дата, номер секції — набирається моно.

## Перезібрати

```bash
node marketing/export.mjs             # усі PNG-креативи
node marketing/export.mjs --preview   # + повносторінкове превʼю деку
node marketing/render-reel.mjs        # відео (обидва бітрейти)
node marketing/render-board.mjs       # кадри сторіборду
node marketing/bundle.mjs             # один файл
node marketing/verify-bundle.mjs ../prostir-marketing.html
node marketing/check-layout.mjs       # 1920 / 1440 / 1024 / 760 / 420
```

Кадри продукту (`shots/`) знімаються з живого застосунку окремо:

```bash
PERF=1 CI=1 npx playwright test _marketing-shots _marketing-public
```

## Чотири рішення, які варто знати, перш ніж щось міняти

**1. Кадри продукту справжні, а не намальовані.** Вони знімаються тим самим
харнесом, що й e2e-тести, у потрійній щільності. Намальований мокап
розходиться з продуктом на першій же правці інтерфейсу — і реклама починає
обіцяти те, чого в застосунку немає.

**2. Плитки, слайди й Stories мають ОДНЕ джерело.** Розмітка живе в масивах
`TILES` / `SLIDES` / `STORIES` всередині `index.html` і рендериться звідти і в
мокап профілю, і у великий перегляд, і в PNG. Копія в трьох місцях розійшлася б
за один раунд правок.

**3. Лічильник слайдів підставляється З ПОЗИЦІЇ в масиві** (`{IDX}`), а не
вписується руками. Перша редакція мала два різні лічильники в одній каруселі —
обкладинка казала «1 / 7», а слайди помилок «1 / 5».

**4. Відео рендериться покадрово, а не записом екрана.** Запис у реальному часі
віддає те, що встиг намалювати браузер під навантаженням; тут кожен кадр
рендериться окремо через `currentTime` на анімаціях.

### Пастка, на якій цей рілз уже згорів

Перший прогін рендера дав **15 секунд чорноти**: ffmpeg завершився успішно,
файл важив 2,7 МБ, і побачити дефект можна було тільки оком. Інлайновий
`style="animation:…"` **скидає** `animation-fill-mode` і
`animation-timing-function` до початкових значень — тобто правило класу, яке їх
задавало, не діяло, і поза активною фазою лишався базовий `opacity:0`.

Другий дефект того ж класу виявився одразу за першим: `both` на анімації
**виходу** заповнює назад, тобто тримає `opacity:1` весь час ДО свого старту —
і три сцени показувались одночасно.

Тому `render-reel.mjs` перед рендером перевіряє інваріант таймлайну: у шести
контрольних точках видно **рівно одну** сцену. Нуль означає чорний кадр, більше
однієї — накладення. Якщо правите анімацію рілза, ця перевірка має лишитись.

### Друга пастка: зелений збирач із дірками у виході

Антивакуум `bundle.mjs` спершу шукав зовнішні шляхи регексом, який чекав лапку
**одразу** за `src`, тобто `src="shots/…"` не матчив ніколи — і збирач спокійно
віддав «самодостатній» файл із вісьмома битими зображеннями. Тому перевірка
тепер двошарова: джерельна (підрядків `shots/`, `fonts/`, `creatives/` у виході
бути не може) і **на рендері** — `verify-bundle.mjs` відкриває зібраний файл і
вимагає `naturalWidth > 0` від кожного `<img>` та нуль зовнішніх запитів.

### Третя: експорт знімає ОБЛАСТЬ, а не вузол

Креативи верстаються в справжніх пікселях Instagram і масштабуються для показу
трансформом; у `?export=1` трансформ знімається. Але треки `minmax(0,1fr)` не
ростуть під 1080 px, тож сусідні креативи налазять один на одного — і знімок
елемента забирає їх разом із собою. Тому в режимі експорту розкладки немає
взагалі: `display:block`.

## Обмеження середовища

ffmpeg у пісочниці зібраний із `--disable-everything`: єдиний відеокодек — VP8,
PNG-декодера немає взагалі, а фільтра `format` немає теж. Звідси JPEG на вході,
WebM на виході і заборона просити будь-яку конвертацію пікформату. Для доставки
в Instagram майстер конвертується в MP4/H.264 на машині з повним ffmpeg:

```bash
ffmpeg -i reel-15s.webm -c:v libx264 -preset slow -crf 18 -pix_fmt yuv420p reel-15s.mp4
```
